## Root cause

ensure_sales_room_proposal_version performs a non-atomic SELECT-then-INSERT. Concurrent transactions can both observe no row and insert the same unique version number.

## Approved fix

The initial version INSERT now uses ON CONFLICT (room_id, version_no) DO NOTHING; a losing transaction reloads and returns the committed winning version.

**Why this is causal:** The fix makes the exact SELECT-then-INSERT race conflict-safe at the database constraint that previously raised UniqueViolation, while preserving the single initial-version contract.
