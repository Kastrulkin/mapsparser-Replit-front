# ПРАВИЛА РАБОТЫ

## 1. Работай с доказательствами

Каждое существенное замечание должно содержать:

- уникальный ID;
- категорию;
- приоритет;
- описание проблемы;
- бизнес- и пользовательский эффект;
- технический риск;
- конкретное доказательство: файл, строки, команда, лог, тест, профиль или измерение;
- корневую причину;
- предлагаемый способ исправления;
- риск самого исправления;
- критерий приёмки;
- способ проверки результата.

Не выдавай предположения за найденные ошибки.

## 2. Не ограничивайся рекомендациями

Твоя задача — не просто подготовить отчёт, а самостоятельно исправить подтверждённые проблемы.

После аудита:

1. сформируй план;
2. расставь приоритеты;
3. начни исправления;
4. добавь тесты;
5. проверь изменения;
6. проведи независимый review;
7. исправь замечания review;
8. повтори цикл до выполнения критериев готовности.

Не останавливайся после составления списка проблем.

## 3. Не переписывай систему ради красоты

Запрещены бессмысленные «сеньорские» рефакторинги:

- переход на микросервисы без подтверждённой необходимости;
- замена рабочего фреймворка ради моды;
- массовое создание абстракций;
- переписывание модулей без тестов и измеримой выгоды;
- внедрение новых зависимостей только ради небольшого сокращения кода;
- изменение пользовательской логики без понимания бизнес-смысла.

Предпочитай минимальные, проверяемые и обратимые изменения, которые устраняют корневую причину.

## 4. Безопасность изменений

Перед началом:

- проверь `git status`;
- не затирай незакоммиченные изменения пользователя;
- зафиксируй текущую ветку и commit;
- создай отдельную рабочую ветку, если это не разрушает текущий процесс;
- не выполняй push, merge, deploy или публикацию без явного разрешения;
- не изменяй production-данные;
- не отправляй реальные письма, сообщения, платежи или уведомления;
- не вызывай внешние интеграции с необратимым эффектом;
- не удаляй данные;
- не ротируй ключи;
- не выполняй необратимые миграции;
- не помещай секреты в код, логи, документацию или тестовые данные.

Для внешних интеграций используй безопасные тестовые режимы, моки или заглушки.

Все изменения схемы данных должны быть:

- обратно совместимыми;
- по возможности обратимыми;
- безопасными для rolling deployment;
- снабжёнными планом rollback;
- протестированными на копии или тестовой базе.

## 5. Автономность

Не проси меня пересказывать то, что можно определить по коду, документации, конфигурации, истории Git или работающему приложению.

Принимай разумные технические решения самостоятельно.

Останавливайся для согласования только перед:

- необратимым изменением данных;
- существенным изменением продуктового поведения;
- сменой ключевой технологии;
- дорогостоящей инфраструктурной миграцией;
- изменением публичного API, которое нельзя сделать обратно совместимым;
- действием в production;
- отправкой информации или сообщений внешним пользователям.

Все остальные решения принимай самостоятельно и документируй.

# СИСТЕМА ПРИОРИТЕТОВ

Используй следующие уровни:

- P0 — возможная утечка или потеря данных, обход авторизации, компрометация системы, критический сбой всего продукта.

- P2 — существенные проблемы производительности, надёжности, UX, тестирования или сопровождения.

Дополнительно для каждого пункта оцени:

- вероятность;
- воздействие;
- масштаб последствий;
- трудоёмкость;
- blast radius исправления;
- уверенность в выводе.

Раздели задачи на:

1. обязательно до демонстрации партнёру;
2. обязательно до промышленного запуска;
3. допустимо выполнить после запуска.

# ЭТАП 3. ИСПРАВЛЕНИЯ

Работай небольшими логическими пакетами.

Для каждого пакета:

1. выбери ограниченную группу связанных findings;
2. воспроизведи проблему;
3. добавь failing test или другой проверяемый критерий, когда это возможно;
4. исправь корневую причину;
5. выполни targeted tests;
6. выполни относящиеся lint/typecheck;
7. проверь diff;
8. запусти независимый `/review` или отдельного reviewer-субагента;
9. исправь подтверждённые замечания;
10. выполни полный подходящий набор проверок;
11. обнови документацию;
12. зафиксируй измерения до и после;
13. сделай отдельный локальный commit с понятным сообщением, если репозиторий и состояние пользователя позволяют это безопасно;
14. обнови `PROGRESS.md` и `HANDOFF.md`.

Не смешивай в одном пакете:

- безопасность;
- масштабный рефакторинг;
- обновление десятков зависимостей;
- изменение схемы;
- визуальный redesign.

Для рискованных изменений используй:

- feature flags;
- backward-compatible API;
- expand–migrate–contract;
- двойное чтение или запись только при реальной необходимости;
- план rollback;
- постепенное включение.
