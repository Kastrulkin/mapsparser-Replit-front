# План изменений LocalOS по обсуждению 5 сентября 2026

Статус: первый этап UX и надёжности выпущен в production 5 сентября после согласия пользователя, резервного копирования и четырёх миграций. Internal compiled-script пилот подготовлен и локально проверен, его production-исполнение выключено. Выполненные проверки, ограничения и оставшиеся этапы перечислены в [отчёте о реализации](LOCALOS_RELEASE_2026-09-05.md). Полный перевод backend/SDK пока не завершён. Исходный план ниже сохранён как критерий приёмки, а не как заявление о выполнении всех пунктов.

План охватывает архитектуру backend, надёжность и проверки, compiled AI в уточнённом пользователем значении, навигацию, персональный экран «Сегодня», предложения персонализации, пользовательские сценарии агентов и партнёрств.

**Целевой результат.** LocalOS остаётся модульным приложением на Flask/PostgreSQL с отдельными процессами исполнения. Пользователь описывает процесс, ИИ создаёт скрипт, система проверяет его, пользователь утверждает конкретную версию. При запуске выполняется этот скрипт без модели. Постоянная главная «Сегодня» показывает актуальную работу; основные направления доступны прямо из меню. Смена обычного приоритета главной предлагается по наблюдаемому использованию и применяется после согласия пользователя.

Последнее решение обсуждения определяет поведение главной: `/dashboard` продолжает открывать «Сегодня». Выбранный приоритет меняет содержание «Сегодня», а не автоматически перенаправляет пользователя в раздел. Идея отдельного стартового раздела была заменена этой моделью.

**Зафиксированные ограничения.**

- Compiled script не вызывает LLM при исполнении, в том числе через скрытые вызовы SDK или доменных методов. Генерация и изменение программы могут использовать ИИ.
- Утверждённая программа неизменяема. Изменение кода, существенных правил, разрешений, расписания или назначения создаёт проверяемую новую версию.
- Повторяемость означает одинаковое поведение при одинаковых входах, версии программы и зафиксированных внешних наблюдениях. Изменение данных у провайдера может закономерно изменить результат.
- Утверждение программы не отменяет существующие правила согласования публикаций, отправок, платежей и массовых изменений. Подтверждённые внешние действия связываются с точным содержимым и областью разрешения.
- Общие бизнес-данные и предпочтения пользователя разделены. Доступ всегда проверяет backend.
- Текущие blueprints, версии, runs, approvals, prospectingleads и доменные сущности переиспользуются. Перенос на новый механизм не создаёт вторую CRM или самостоятельный продукт агентов.
- Существующие API и активные задания сохраняют совместимость до проверенной миграции.

**Порядок выпуска.** Каждая строка — отдельно проверяемый результат; общий план не является разрешением немедленно запускать эти работы или менять production.

| Выпуск | Результат | Работы | Условие начала |
| --- | --- | --- | --- |
| 0 | Контракты, воспроизведения и обязательные проверки | G0 | Подтверждение объёма реализации |
| 1 | Надёжные транзакции, задания и единая граница внешних действий | B1, B2 | G0 |
| 2 | Прямое меню и «Сегодня» с ручным выбором приоритета | U1, U2; начало сбора событий U3 | G0; готовность миграции предпочтений и проверок доступа |
| 3 | Генерация и безопасная проверка настоящих скриптов | A1, A2 в preview | G0; договорённый контракт SDK |

Выпуски UX и подготовки компилятора могут готовиться независимо от полного разделения backend. Production-исполнение сгенерированных скриптов зависит от надёжной очереди, SDK и изоляции. Рефакторинг доменных модулей ведётся постепенно и не задерживает полезные изменения интерфейса.

**G0. Закрепить решения и создать надёжную проверку изменений.** Ответственность: backend, frontend, QA и эксплуатация.

Текущие документы Compiled AI v2 допускают model steps во время исполнения. Перед реализацией нужно обновить их описание под утверждённые скрипты без runtime LLM и обозначить старый контракт как совместимый legacy. Обновить согласованно README, PRODUCT, DESIGN и существующие архитектурные документы. Отдельно зафиксировать, что «Сегодня» остаётся общей главной.

- Составить реестр проверяемых гипотез с триггером, ожидаемым поведением и точкой входа. Приоритет: implicit commit, потеря worker, блокировка agent queue, повтор Telegram event, version bindings, Maton dispatch, ошибки истории Operator и локализация «Сегодня».
- Снять baseline на изолированном окружении: миграции, релевантные backend/frontend tests, оба frontend build, typecheck, queue latency, ошибки API и время до полезного действия в UI. Фиксировать известные старые сбои отдельно.
- Сделать обязательный CI для changed domains, контрактов доступа/approval и затрагиваемых UI. Добавить сборку public/dashboard, проверку типов и существующие dependency/security gates.
- Использовать отдельный PostgreSQL и тестовые адаптеры провайдеров. Убрать production URL по умолчанию из mutating smoke. Обязательные проверки не должны считаться пройденными после пропуска из-за отсутствующих secrets.
- Вводить строгую типизацию по затронутым DTO и модулям. Сначала зафиксировать существующий долг; не менять весь TypeScript-конфиг одним несвязанным патчем.

Приёмка: PR с нарушенным tenant scope, approval или контрактом запуска не проходит CI; тестовая мутация не может попасть на production; baseline содержит выполненные и пропущенные проверки с причинами.

**B1. Явные транзакции, единый доступ и управление схемой.** Ответственность: backend и БД.

- Найти runtime DDL в активных маршрутах и сервисах. Сверить каждую используемую таблицу, колонку и индекс с Alembic; отдельно учесть legacy/debug-скрипты.
- Внести недостающую схему в расширяющие миграции. Удалять runtime CREATE/ALTER после проверки существующих установок. При старте проверять совместимость схемы; запросы пользователей её не создают.
- Разделить роль мигратора и обычную роль приложения после полного переноса активного DDL. Сохранить защиту от конкурентного применения миграций.
- Ввести явный unit of work: commit при успешной команде, rollback при ошибке, закрытие соединения без скрытого сохранения.
- Перед изменением поведения DatabaseManager проверить callers, которые рассчитывают на commit при close. Переводить их по доменам с тестами; глобальное переключение без инвентаризации недопустимо.
- Ввести общий контекст доступа: actor, tenant/business, network scope, роль, ограничение сессии. Сервисы получают этот контекст вместо разрозненных user_id/is_superadmin.
- Сохранить общую защиту demo-сессий и дополнить сервисные проверки. Подтверждённой эксплуатации Content Voice через demo в аудите нет: этот случай блокируется глобальным фильтром.

Приёмка: обычный GET не выполняет DDL; исключение после промежуточной записи не сохраняет частичную операцию; чужой business и scope ограниченной сессии отвергаются; старая совместимая версия приложения работает с расширенной схемой.

**B2. Очереди, триггеры и внешние действия.** Ответственность: backend и эксплуатация.

- Описать общий жизненный цикл задания: queued → running → waiting_approval / retry_wait → completed / failed / cancelled. Доменные очереди могут храниться отдельно, но имеют одинаковые гарантии владения, восстановления и наблюдаемости.
- Добавить восстановление потерянных running-заданий Operator, сроки исполнения, backoff, ограничения попыток и корректное завершение при остановке процесса.
- Убрать долгие транзакции вокруг сетевой/AI-работы. Claim, heartbeat, фиксация результата шага и финализация выполняются короткими транзакциями.
- После изменения транзакционных границ ввести lease/attempt token: устаревшая попытка не может записать состояние или инициировать новое внешнее действие. Heartbeat продлевает владение отдельно.
- Очистка просроченных agent runs не должна блокировать получение независимых заданий. Проверить её вместе с SKIP LOCKED на настоящем PostgreSQL, а не только на mock cursor.
- Направить web, Telegram и scheduler через единый admission/enqueue: доступ, версия, проверка входа, текущие подключения, лимиты, бюджет и идемпотентность.
- Добавить durable inbox для событий. Telegram дедуплицируется с учётом подключения и provider event ID; расписание — по automation и конкретному временному слоту с учётом часового пояса. При первом принятии события фиксируется версия; retry не выбирает новую active version.
- При нескольких подходящих автоматизациях хранить отдельные связи event → run, не перезаписывая единственную ссылку последним запуском.
- Объединить version-aware preflight: проверять bindings утверждённой версии и фактическое состояние соответствующих подключений. Metadata используется для представления и defaults.
- Любой режим, включая one_off, проходит проверку исполняемой версии. Отдельно проверить гипотезу обхода validation; отсутствие activation у разового запуска само по себе не является дефектом.
- Сохранить существующие ActionOrchestrator ledger/outbox и stable idempotency keys. Перевести прямую Maton-ветку на ту же границу.
- Разделить процессы выполнения: браузерный парсинг, AI/agent jobs, compiled scripts, provider dispatch, расписания/обслуживание. Ограничить concurrency по провайдеру и бизнесу.

Для внешней отправки закрепить состояния «запрос принят», «результат неизвестен», «отправлено», «доставлено», «прочитано». При неопределённом исходе сначала сверка с провайдером. Где провайдер не поддерживает идемпотентность или сверку, автоматический повтор требует отдельного решения. Гарантировать exactly-once для произвольного внешнего API нельзя.

Приёмка: повтор webhook даёт одно принятое событие и один логический запуск на автоматизацию; падение worker не теряет задачу; длинный parser не задерживает независимую очередь; вторая попытка не меняет состояние после потери lease; подтверждённая операция не повторяется при retry; неоднозначная отправка попадает в сверку.

Важная корректировка аудита: в текущем обычном worker-пути блокировка строки защищает живой run от одновременного reclaim. Установленный риск — блокировка очереди длинной транзакцией. Fencing становится необходимой частью целевого решения с короткими транзакциями. PostgreSQL описывает SKIP LOCKED как механизм для нескольких потребителей очереди: [документация PostgreSQL 16](https://www.postgresql.org/docs/16/sql-select.html).

**B3. Разделять backend по ответственности и реальным зависимостям.** Ответственность: backend; работа выполняется постепенно внутри остальных выпусков.

| Домен | Владеет |
| --- | --- |
| Доступ и организации | Пользователи, сети, бизнесы, роли, scope |
| Карты и репутация | Парсинг, карточки, аудит, услуги, отзывы |
| Контент | Голос бизнеса, материалы, планы, черновики, публикации |
| Привлечение | Лиды, партнёрства, инфлюенсеры, кампании и ответы |
| Финансы | Импорты, показатели и подтверждаемые финансовые операции |
| Автоматизация | Программы, версии, запуски и пользовательские решения |
| Интеграции | Подключения, адаптеры, callbacks и текущее состояние провайдеров |

- Слои внутри домена: транспорт API → прикладной сценарий → правила → репозитории/адаптеры.
- Сначала выделить конкретные сценарии, которые одновременно нужны web, Telegram и script SDK. Все поверхности вызывают один прикладной сценарий.
- Убирать globals()/shared namespace и обратные импорты в main по одному модулю, сохраняя временные compatibility wrappers.
- Ввести небольшие проверки разрешённых зависимостей и контрактов. Ограничения размера файлов использовать только как вспомогательную защиту.
- Сверить старый PROJECT_HARDENING_PLAN с уже выполненными выделениями модулей: не повторять завершённую работу по устаревшему списку.

Приёмка: прикладной сценарий тестируется без импорта полного Flask app; domain tests явно показывают зависимости; web и SDK дают одинаковый результат и правила доступа; compatibility wrapper имеет перечисленных callers и условие удаления.

**A1. Настоящий компилятор пользовательского процесса в программу.** Ответственность: backend/AI engineering и QA.

Первый целевой runtime — фиксированная версия Python в подготовленном окружении. Это сокращает число языков и использует текущую экспертизу проекта. Скрипт хранится отдельным неизменяемым артефактом, а не выполняется через eval/exec внутри Flask.

- Описание процесса преобразуется в требования: источники, параметры, точные правила, исключения, результат, расписание и ограничения.
- Неопределённые критерии вроде «подходящий партнёр» уточняются до проверяемых правил. Если задача требует интерпретации нового текста моделью каждый раз, компилятор честно сообщает, что она не укладывается в режим без runtime AI; не маскирует её под compiled script.
- ИИ генерирует исходный код, manifest, пояснение поведения и предлагаемые примеры проверки.
- Проверка включает синтаксис, допустимые зависимости/SDK, схемы данных, ограниченные операции, эталонные тесты и пробный запуск в изоляции.
- Тесты, придуманные самим генератором, дополняются независимыми эталонными входами и ожидаемыми результатами, выведенными из требований пользователя.
- Пакет версии содержит код и hash, входную/выходную схемы, версию runtime и SDK, lock зависимостей, binding refs, права, лимиты, trigger, проверочные доказательства и описание изменений.
- Сохранить происхождение: версия генератора/модели/инструкций и время сборки. Проверять hash перед каждым запуском.
- Статусы: черновик → проверяется → требует исправления / готов к утверждению → утверждён → включён / приостановлен / заменён.

Приёмка: новый запуск использует ровно утверждённый артефакт; изменение кода не затрагивает работающую версию; неподдерживаемые операции блокируются до активации; пробный запуск и рабочий режим используют один артефакт с разными разрешёнными адаптерами эффектов.

**A2. Изолированный исполнитель и SDK LocalOS.** Ответственность: backend и эксплуатация.

- Подготовить небольшой SDK для чтения разрешённых данных, чистых преобразований, сохранения результата и создания предложений действий.
- Capability contract задаёт input/output schema, нужные права, допустимые данные, внешние эффекты, idempotency/recovery и признак использования модели.
- В compiled-safe allowlist входят только операции без модели, включая их внутренние зависимости. Генерация текста через существующую AI-capability не проходит эту проверку.
- Скрипт не получает прямой доступ к PostgreSQL, provider credentials, Docker socket или файловой системе хоста. Брокер SDK проверяет tenant, run, версию, текущие права и доступные операции; полномочия исполнения краткоживущие и узкие.
- Изолированный runner имеет ограничения CPU, памяти, времени, числа процессов, размера вывода и временного хранилища. Окружение и зависимости подготовлены заранее; установка произвольных пакетов во время запуска исключена.
- Прямой внешний egress ограничен; провайдеры доступны через контролируемый SDK/broker. LLM endpoint недоступен, а число runtime model calls контролируется отдельной проверкой.
- Проверить выбранную изоляцию как границу для сгенерированного кода. Для пилота использовать отдельный исполнитель с жёстким профилем; до широкой многопользовательской эксплуатации провести отдельную проверку угроз и необходимости усиленного sandbox runtime.
- Фиксировать результаты SDK-операций и checkpoints. При восстановлении возвращать сохранённый результат завершённой операции по стабильному ключу вместо повторного внешнего эффекта.
- Для replay зафиксировать входы и внешние наблюдения; текущее время, случайность и окружение передавать контролируемо там, где они нужны процессу.
- Разделить учёт стоимости генерации программы и исполнения. Отсутствие LLM-вызова не означает отсутствие вычислительных или provider расходов; существующие тарифы не менять без отдельного решения.

Приёмка: 0 runtime model calls; один результат на одинаковом fixture/replay; нельзя прочитать чужой tenant, секрет или host file; бесконечный цикл завершается лимитом; соседняя задача продолжает работу; crash после SDK-операции не повторяет подтверждённый эффект.

Docker отдельно описывает риски доступа к daemon/socket и изоляции конфигурации, а также необходимость лимитов ресурсов: [безопасность Docker](https://docs.docker.com/engine/security/), [ограничения ресурсов](https://docs.docker.com/engine/containers/resource_constraints/). Наличие контейнера само по себе не считается пройденной проверкой sandbox.

**A3. Пользовательское утверждение, пилот и миграция агентов.** Ответственность: frontend, backend и QA.

- Один последовательный путь создания: задача → правила и параметры → проверка на примере → утверждение версии → способ запуска.
- Перед утверждением показать поведение простым языком, входы/источники, пример результата, возможные изменения, права и лимиты. Исходный код и технические доказательства доступны во втором слое.
- Сгенерированное описание сопоставить с manifest и фактически разрешёнными SDK-операциями: обещания модели не заменяют проверку программы.

Rollback интерфейса возвращает старое представление, сохраняя совместимые данные. Rollback script runtime прекращает новые admission, явно обрабатывает уже запущенные задания и возвращает последнюю совместимую утверждённую версию. Не удалять журналы, артефакты или предпочтения для отката.

Предпочитать частичный согласованный выпуск затронутых сервисов. Если меняются окружение исполнения или зависимости, нужен соответствующий образ, а не только копирование исходника.
