# Входящее обращение → решение сотрудника

Статус: **internal**, первый подготовительный этап white label. Дата: 17.11.2026.
Активация конкретной организации и проверка с живым сотрудником фиксируются отдельно;
наличие API не означает приёмку почты, команды и автоматизации целиком.

19.11.2026: [включение для владельца Riderra и фактические проверки](inbound-case-pilot-activation-20261119.md).

## Границы и переиспользование

LocalOS хранит универсальную подготовку, версию, согласование и результат в
`agent_trigger_events`, `agent_trigger_run_links`, `agent_runs`, `agent_artifacts`,
`agent_approvals`. Используется существующий `AgentBlueprintRunner` с узким
подготовительным preset, а не второй движок заданий или компилятор.

Источник хранит исходное письмо, предметные проверки и назначение сотрудника.
В Riderra это AI Inbox, `orderPreparationReview`, `OpsTask` и существующий Telegram
webhook. Нет второго сборщика почты, планировщика, бота с тем же токеном или CRM.
Заказы, трансферы, цены, водители и их HumanApproval остаются в Riderra.

Сверка OpenClaw 17.11: службы riderra-email-bridge и riderra-order-draft работают;
установленный `integrations/riderra_order_draft` уже имеет classify/extract/validate.
Этот выпуск их не заменяет и не делает новых модельных вызовов. Готового действия,
которое связывает tenant/сотрудника Riderra с версией и согласованием LocalOS, там нет:
для этой продуктовой границы нужен небольшой доменный адаптер.
См. также [состояние OpenClaw](../OPENCLAW_CURRENT_STATE_20261012.md).

**Первый режим — выбранное обращение, существующая подготовка источника и ручная
проверка.** Классификация обозначена `source_preparation`. Новая LLM-классификация,
самостоятельный генератор и платный запуск не добавлены. Передача в LocalOS включает
только выбранный черновик/краткий контекст; исходный почтовый ящик не копируется.
Текст остаётся внутренними данными двух систем; к внешней модели он не передаётся.
Для будущих модельных шагов обязательна действующая PII-граница LocalOS и бюджет.

## Контракт v1

Закрытые маршруты, заголовок `X-LocalOS-Agent-Key`:

| Маршрут | Scope | Результат |
| --- | --- | --- |
| `POST /api/agent-api/inbound-cases` | `cases:prepare` | Сохранить неизменяемую версию, открыть проверку |
| `GET /api/agent-api/inbound-cases/{run_id}` | `cases:read` | Текущий текст, статус, решение |
| `POST /api/agent-api/inbound-cases/{run_id}/review` | `cases:review` | Принять, отклонить или запросить уточнение |

Общие поля: `source_system`, `source_tenant`, `actor_id`. Подготовка дополнительно:
`source_id`, `source_version`, `reviewer_actor_id`, `title`, `summary`,
`classification`, `missing_information[]`, `proposed_reply`, необязательный
`replaces_run_id`. Серверное связывание определяет бизнес, пользователя и pinned
версию. Роль, `business_id` и разрешения из тела запроса не принимаются.

Результат: `run_id`, `business_id`, `status`, `approval_id`, `review_hash`, `review`,
`resolution`, `updated_at`, `credits_spent=0`, `preparation_only=true`.
Решение передаёт **полный** `review_hash`, `source_version`, `decision`, `reply`,
`reason`. `accepted` сохраняет ровно показанный текст, без недостающих обязательных
сведений. Это принятие черновика, а не разрешение внешней отправки.

Повтор той же версии возвращает тот же запуск. Другое содержимое с тем же ключом
даёт 409. Редактирование создаёт новый просмотр и адресно отменяет прежний;
прочие обращения продолжают ждать своих решений. Отзыв членства, другой бизнес,
чужой сотрудник, изменённый источник/план и устаревший hash отклоняются.
Источник обязан проверять фактическую свежесть своих данных перед решением.
При неопределённом сетевом исходе повторяется тот же ключ, не создаётся новый.

## Подключение

По умолчанию API выключен: `LOCALOS_INBOUND_CASES_ENABLED=false`.
Существующим клиентам scopes автоматически не выдаются. Сначала подготовить
явное связывание организации и существующих активных участников:

```json
{
  "business_id": "LOCALOS_BUSINESS_ID",
  "source_system": "riderra",
  "source_tenant": "RIDERRA_TENANT_ID",
  "actors": {
    "RIDERRA_USER_ID": {
      "user_id": "LOCALOS_USER_ID",
      "operations": ["prepare", "read", "review"]
    }
  }
}
```

Проверка без записи:

```sh
PYTHONPATH=src python scripts/provision_inbound_case_pilot.py --config /secure/binding.json
```

После согласования конкретного связывания: `--apply --key-file /secure/riderra-case.key`.
Ключ создаётся в новом файле с правами 0600, не выводится и не попадает в Git.
Повторное применение не меняет ключ или grant. Скрипт не добавляет членство или
новые права сотруднику. Он создаёт только узкий client и фиксированный preset
на существующих таблицах. Включение среды выполняется отдельно с резервной копией.
На стороне Riderra см. `docs/integrations/localos-case-pilot.md`.

## Проверки и следующий этап

Тесты `tests/test_inbound_case_pilot.py` работают с отдельной временной локальной
PostgreSQL-базой и настоящими таблицами/runner. Проверяются повтор, одновременная
доставка, независимость обращений, изменение текста, свежесть, пауза, восстановление,
границы HTTP/scopes/tenant и отсутствие модельных вызовов.

Далее: один выбранный реальный источник, решение владельца, затем один сотрудник.
Автоматический приём почтовых событий подключается к существующему ingest только
после этого прохода. Эскалации, руководительские сводки, измерение экономии времени
и повторение в Органике — следующие этапы, не заявлены готовыми этим выпуском.
Метрики первого этапа берутся из существующих дат событий/решений: число обращений,
время ожидания, доля уточнений/отклонений, повторы, ошибки и фактические расходы.
