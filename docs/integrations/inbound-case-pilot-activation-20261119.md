# Riderra → LocalOS: включение подготовительного пилота

Дата проверки: 19.11.2026. Статус: `internal`, включён для одной организации
Riderra и одного существующего проверяющего — владельца Александра Демьянова.
Полный переход операционных процессов и подключение команды не завершены.

## Включение

Создан узкий служебный клиент с `cases:prepare/read/review` и явным соответствием
Riderra tenant/user → LocalOS business/user. Проверено существующее активное
членство с `operations.write`, без выдачи новых ролей или членств. Ключ сохранён
в закрытой конфигурации серверов, в Git и уведомлениях его нет.

На LocalOS восстановлено наследование действующего PII-профиля из канонического
Compose fragment. Все пять потребителей проверены после пересоздания и повторно
19 ноября: обязательная активация, readonly-файлы клиента/активации, закрытая сеть
и работающие процессы. Сохранены прежние образы, команды, источники и остальные
настройки. Автоматические миграции при этом не запускались.

Закрытый HTTP API без ключа отвечает 401. С действующей привязкой Riderra сохраняет
подготовку в существующих LocalOS runs/artifacts/approvals. Модели и внешние
обработчики не вызываются: preset остаётся preparation-only.

## Фактическая проверка

- Существующий источник Riderra → одна назначенная задача → один run LocalOS.
- Повтор подготовки возвращает те же задачу, run и хеш просмотра. Исходник
  не меняется, дополнительного списания нет.
- Реальные `/localos` и `/case` в существующем Riderra-боте показали задачу и
  полный текст из LocalOS.
- В живом AI Inbox исправлен текст через форму и создана новая версия.
  После исправления восстановления кабинета повторное открытие показывает
  новую версию; прежняя закрыта заменой и остаётся в истории.
- Расходы подготовительного сценария — 0 кредитов, модельных вызовов — 0,
  отправок клиенту — 0. Заказ, цена и Sheets этим сценарием не изменялись.
- Владелец принял новую версию кнопкой Telegram. Проверены `accepted` и
  `completed` в LocalOS, `done` в Riderra и восстановление «Черновик принят»
  с исправленным текстом readonly после перезагрузки живого кабинета.
  `external_dispatch_performed=false`, исходник сохранился, расходы — 0.
  Этот подготовительный проход завершён; полный white label остаётся поэтапной работой.

На Riderra устранены препятствия: локальный маршрут существующего SSH/SOCKS-туннеля,
отсутствовавшая авторизация прокси, фильтр poller без `callback_query` и выбор
закрытой старой задачи по `updatedAt`. Новых ботов, коннекторов, планировщиков
и генераторов не создавалось. Девять целевых тестов Riderra прошли, включая
восстановление принятой версии и повтор доставки нажатия.

Черновик существующей подготовки спрашивал уже известный возраст ребёнка.
В проверке его исправили вручную как пользователь. Качество автономной генерации
этим не принято; новые платные вызовы не выполнялись.

## Эксплуатация и следующий этап

Резервные копии сохранены в `/opt/seo-app/backups/inbound-case-activation-*`
и соответствующих каталогах Riderra. Секретные файлы имеют закрытые права.
Откат флага пилота не должен отключать PII и удалять историю обращений.
Границы компонентов описаны в [основном контракте](inbound-case-pilot.md).

Далее: явная привязка одного сотрудника, цикл уточнения/возврата на доработку,
автоматический intake на существующих событиях, эскалации и сводка руководителю.
Проверка аналогичного сценария в другой организации ещё требуется. Telegram
остаётся интерфейсом; состояния и решения принадлежат LocalOS/Riderra.
