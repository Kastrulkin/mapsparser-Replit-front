# Технический план внедрения: аутрич из LocalOS/MAX

Дата: 12 ноября 2026. Статус: **кандидат реализации T0–T6; проверка PostgreSQL и T7 остаются открытыми**. Фактическое поведение и ограничения — в [записи релиза](releases/2026-11-12-miniapp-outreach.md). Наличие кода не означает выкладку или успешный живой тест.

## 0. Уточнение после аудита существующей реализации

[Проверка веток, коммитов и прошлых выкладок](LOCALOS_OUTREACH_IMPLEMENTATION_AUDIT_20261112.md) подтвердила: существенная часть работ уже сделана. Предыдущая редакция завысила объём новой разработки, потому что текущий checkout не содержит ряда файлов из готовой MAX-версии.

Подтверждены: `f23a30e` — платформенные входящие/синхронизация/поиск в миниаппе; `ff91091b8` — веб-поиск; октябрьские исправления Operator/worker; клиентские `PreparedPartnershipMessages`/`PartnershipGroupLaunch`; фактические архивные выкладки 12–16 октября. Свежая проверка Riderra на текущем сервере остаётся отдельной задачей.

**Правило исполнения:** сначала объединить и сохранить найденную реализацию; разработать только перечисленную разницу. Не создавать новый поиск, почтовый коннектор, очередь, approval, экран запуска подборки или бюджетный механизм вместо уже существующих.

## 1. Цель и границы релиза

Первый релиз закрывает полный сценарий на существующем Riderra: найти подключённую почту → показать условия поиска → запустить согласованный поиск → сохранить компании → подготовить и разрешённо отправить письмо → обновить ответы → продолжить после повторного открытия MAX. Затем тот же механизм проверяется на обычном клиентском доступе.

Riderra — проверочный бизнес, а не отдельная реализация:

- business_id: `edbd961a-273f-4f15-836e-33aacc0aa0e3`;
- ожидаемый sender_account_id: `5e9ce7db-44d1-49dc-9aed-b35ed7174089`;
- ожидаемый адрес: `riderracs@gmail.com`.

В коде общих API не зашивать эти значения; использовать их в приёмке и существующих специальных правилах Riderra. Почту повторно не создавать. Отправки и расходы используют действующие разрешения/согласования.

Контент и редактор автоматизаций — следующий релиз T8. Общие источники, доступы, задания и история первого релиза должны подходить для их подключения.

## 2. Зафиксированные технические решения

1. Flask/PostgreSQL, существующие Operator, worker и durable jobs остаются исполнительным контуром.
2. Источники истины: `outreach_sender_accounts`, `outreach_campaigns`, `outreach_campaign_touches`, `lead_workstreams`, `outreachsendqueue`, `outreach_inbound_events`, Company Registry. Новую базу лидов/писем, очередь отправок и второй механизм согласований не создавать.
3. Общий клиентский scope получается расширением существующих `operator_platform_outreach.py`, `operator_platform_outreach_api.py` и native outreach routes. Новые модули/алиасы добавлять только при необходимости выделить общий код, а не ради второго набора обработчиков. Существующий платформенный маршрут и формат ответа сохраняются.
4. MAX/Web/Telegram вызывают одни сервисные операции. Чат сохраняет диалог и согласование через существующую транзакцию `process_chat`; интерфейс не собирает собственные фиктивные approvals.
5. Выбор LocalOS даёт действующему администратору платформенный контекст. Для «сделай для Riderra» отдельно разрешается целевой бизнес действия. Системный бизнес LocalOS остаётся якорем истории, а не случайной заменой Riderra. Общеплатформенные поручения сохраняют существующий платформенный контекст.
6. Поиск по умолчанию — уже реализованный `outreach_web_search.py`, routing `_start_search` в новой версии `outreach_continuation.py`; карты/Apify только при явном выборе. На T0 нужен перенос и проверка готовой версии/окружения, а не создание нового веб-поиска.
7. Схему БД по умолчанию не менять. Если T0/T2 обнаружит недостающий индекс/инвариант, оформить точную Alembic-миграцию отдельным пунктом с резервной копией и обратной совместимостью.

## 3. API: переиспользование и минимальное расширение

| Уже существующий контракт | Что менять |
| --- | --- |
| `GET/POST /api/operator/mobile/platform/outreach` в `f23a30e` | Сохранить платформенную версию. Для обычного бизнеса выделить ту же операцию с проверенным scope и целевым business_id; отдельный URL-алиас допустим, второй сервис не нужен. |
| GET платформенного workspace | Уже возвращает входящие, cursor, отправителей, последние поиски и readiness. Обобщить scoped-запросы и принадлежность результата, сохранив совместимость. |
| POST `action=sync` | Уже создаёт `outreach_inbox_sync`. Добавить проверенную клиентскую область и sender/campaign filters; не повторять глобальный сбор от имени клиента. |
| POST `action=search_preview` | Уже использует `process_chat`, `operator_task.preview`, `prepare_new_task_approval`, настоящий action_id. Добавить только разрешённый целевой бизнес и клиентскую форму. |
| `POST /api/operator/actions/<action_id>/confirm` | Уже проверяет согласованные условия и запускает утверждённую операцию. Переиспользовать `confirm_task_start`/`create_and_start`; нового confirm не создавать. |
| `GET /api/operator/mobile/jobs/<job_id>` | Переиспользовать для polling с действующей областью доступа. |
| `GET /api/outreach/messages`, campaign get/edit/review/approve/action | Существующие очередь и кампании; проверить/уточнить клиентский scope без второго независимого списка. |
| `GET/POST /api/partnership/prepared-messages`, `POST /api/partnership/collections/<collection_id>/launch` | Уже используются клиентским миниаппом новой версии; сохранить проверку, digest, расписание и штатную очередь. |

Имена нового клиентского URL, если он понадобится, выбрать на T2 после проверки регистрации существующих blueprint и совместимости. Это небольшой адаптер к перечисленным операциям, а не обязательный набор из шести новых API предыдущей редакции.

Общая авторизация — существующие `require_auth_from_request`, разрешение scope и текущие проверки бизнес-прав. Невалидная сессия — `401`; недостаточно прав — `403`; чужой объект не раскрывается; устаревшие согласованные условия не исполняются. Условия/стоимость показываются до запуска. Существующий `search_preview` может сохранять approval, но не должен создавать поиск/платный вызов до confirm; не смешивать его с чистой функцией просмотра config из старой ветки.

### Результат синхронизации

Сохранить готовый job kind `outreach_inbox_sync` и существующий `result.sync_status=checked|partial|no_sources` из `f23a30e`. Не вводить новый job-status или несовместимое переименование outcome ради интерфейса. Дополнительную детализацию источников расширять обратно совместимо.

При клиентском обобщении сохранить существующие поля и добавить недостающие: `scope`, охват `outreach_replies`, детализацию источников/счётчиков и внутреннюю `result_target`. Для каждого источника: business_id, sender_account_id, channel, status, время успешной проверки, число новых человеческих ответов и безопасный error_code.

`as_of` снимка не выдаётся за дату синхронизации. `no_sources` и неуспех не превращаются в «новых ответов нет». Сырые ошибки, токены и настройки почты не попадают в ответ. Чтение ответов аутрича не обещает обработку всей почты ящика.

## 4. Матрица доступа

| Роль/область | Чтение | Синхронизация, поиск, отправка |
| --- | --- | --- |
| Владелец/редактор бизнеса | Разрешённые данные бизнеса | По действующим правам, готовности, тарифу и согласованиям |
| Пользователь только с чтением | Сохранённые разрешённые данные | Запуск/отправка запрещены |
| Активный superadmin в LocalOS | Разрешённая платформенная сводка с принадлежностью каждого результата | Для разрешённой цели; актуальные права проверяются повторно |
| Demo/impersonation | Только предусмотренные демонстрационные данные | Живые запуски не разрешаются |
| Доступ отозван | Частные результаты очищаются | Задание не продолжает внешние вызовы от имени отозванного актора |

Клиентский job не вызывает глобальный сборщик. Для собственных бизнес-отправителей передавать конкретный sender_account_id; для общего отправителя дополнительно ограничивать кампанию/пакет клиента. Чужой job не возвращается пользователю ради дедупликации.

### T0 — Базовая версия, зависимости и пакет релиза

**Зависимости:** нет. Серверная сверка требует доступного выполнения SSH; остальные подпункты выполняются локально.

**Работа:**

- сопоставить текущую ветку, отдельную MAX-ветку и локальные изменения; для `f23a30e` проверить актуальный remote/состав, а не полагаться на старую запись;
- сохранить исходные пользовательские изменения; сформировать изолированную ветку и manifest только нужных файлов;
- найти фактический web-search маршрут и его контракт, источник цены, ограничения и способ сохранения компаний;
- зафиксировать текущие тестовые падения и TypeScript-диагностику;
- на сервере из `/opt/seo-app`: Compose, версии файлов внутри контейнеров, безопасная сводка флагов app/worker/bot, привязка отправителя, здоровье и последняя синхронизация, состояния кампаний/очереди Riderra. Без новых отправок/поисков.

**Результат:** manifest релиза, карта «существует/нужно перенести/нужно добавить», исходная сводка Riderra и список точных блокеров. Если SSH недоступен, этот подпункт помечен blocked; T1–T6 могут готовиться локально.

### T1 — Единый scope и обнаружение отправителя

**Зависимости:** локальная часть T0.

**Файлы:** `operator_connection_status.py`, `operator_platform_context.py`, `operator_core.py`; общий сервис `operator_outreach_workspace.py` — новый либо извлечённый из платформенного слоя после T0.

**Работа:** централизовать разрешение области чтения и целевого бизнеса команды; учитывать внешние аккаунты и `outreach_sender_accounts`; разделять сохранённое подключение, подтверждённый вход, разрешение отправки и свежесть ответов. Пустой фильтр по названию не доказывает отсутствие ящика. Проверять активность/роль в БД; не доверять только выбору LocalOS или имени бизнеса.

**Проверки:** unit и PostgreSQL на двух бизнесах; обычный клиент, viewer, platform admin, отзыв прав; отсутствие секретов в JSON. Найденный Riderra sender совпадает с существующим, не создаётся новая запись.

**Готово:** разрешение одной области используется одинаково для чтения, постановки задач и получения результата; клиент не получает чужой sender/job.

### T2 — Обобщить существующие API на клиентский scope

**Зависимости:** T1.

**Основа:** `operator_platform_outreach_api.py`, `operator_platform_outreach.py` из `f23a30e`; существующие `operator_api.py`, `outreach_campaign_api.py`, `partnership_leads_api.py` и `api/prospecting/outreach_routes.py`.

**Изменения:** выделить общую проверку scope и адресные запросы из платформенной реализации. Сохранить действующий platform API. Переиспользовать native messages, campaign, prepared-messages и collections launch. Добавить клиентский адаптер только для операций, которых нет в существующих routes.

Читать каноническую принадлежность кампаний/workstream бизнесу. Не удалять все intent-фильтры и не расширять выборку небезопасным OR; противоречивые записи не перепривязывать автоматически. Сохранить ответы workstream без campaign, пагинацию и даты. Новый список отправок/кампаний не создавать.

**Проверки:** настоящие Flask routes и disposable PostgreSQL; владелец/viewer/чужие IDs; platform aggregate; cursor; GET не создаёт jobs и не вызывает провайдера.

**Готово:** найденные existing API доступны разрешённому клиенту и правильно показывают его канонические данные без прав superadmin.

### T3 — Фоновая свежая проверка ответов

**Зависимости:** T2.

**Файлы:** готовые `operator_platform_outreach.py`, `operator_platform_outreach_api.py`, `operator_async_jobs.py`, `operator_platform_context.py`/`operator_core.py`. Общий модуль выделять только как перенос кода, если это упрощает scope. Переиспользуем `outreach_email_reply_service.py`, `outreach_vk_reply_service.py`, Telegram-обработчик из `api/prospecting/audit_generation.py` и существующие receipts/дедупликацию.

**Работа:** сохранить уже готовые enqueue/process/worker dispatch/lease/partial/polling и добавить клиентский scope. Проверить, что существующее поведение удовлетворяет следующим условиям; исправлять только отклонения:

- атомарно проверить активное задание того же пользователя/области/набора источников и создать job при отсутствии; request_id защищает повтор HTTP, повтор после завершённого цикла может создать новую проверку;
- поставить задание и зафиксировать транзакцию до выполнения внешнего чтения;
- вызывать `sync_email_replies(sender_account_id, campaign_id, ...)`, `sync_vk_replies(sender_account_id, campaign_id, ...)`, `_sync_telegram_app_replies(sender_account_id, batch_id, ...)` с проверенными ограничениями;
- не передавать клиентский запрос в глобальный проход всех отправителей; для общих источников ограничивать разрешённые кампании/пакеты;
- повторно проверять права до внешнего вызова и перед выдачей частного результата; обновлять job/message только при действующей lease;
- агрегировать checked/partial/no_sources; сохранять прежнюю дату успешной проверки при ошибке; не дублировать события/уведомления;
- команды «покажи ответы» и «проверь ответы» разводятся по чтению и синхронизации; меню и чат вызывают одну операцию.

**Проверки:** повторные клики, повтор HTTP, параллельный запуск, частичный отказ, ноль источников, общий ящик двух бизнесов, отзыв прав, падение worker и повтор без дубля входящего. Внешние вызовы подменяются в локальных тестах.

**Готово:** одна команда даёт один наблюдаемый цикл проверки и честный результат; не создаёт отправок.

### T4 — Подключить готовый поиск к клиентскому миниаппу

**Зависимости:** T2 и перенос выверенной версии `outreach_continuation.py`/`outreach_web_search.py`.

**Основа:** `search_preview` в `operator_platform_outreach_api.py`; `operator_task`, `prepare_new_task_approval`, `confirm_task_start`, `_start_search`; существующие `process_chat`, credit billing и Company Registry.

**Изменения:** передать разрешённый бизнес/условия из клиентского экрана в этот же путь. Сохранить режим `find_only` для первого прохода, существующие hash/revision, реальный action_id и create_and_start после подтверждения. Не добавлять промежуточную очередь/второй approval и не создавать job до confirm только ради новой схемы API.

Переиспользовать готовый веб-поиск и ограничение Maps/платного Яндекса. Сохранить резервы/receipts/защиту расходов, включая октябрьскую production-совместимость. Проверить сохранение компаний/источников, достигнутый объём, отсутствие дублей и принадлежность Riderra. Сверить readiness/флаги app/worker/bot; при недоступности показывать причину.

**Проверки:** условия совпадают у меню/чата; до подтверждения нет поиска/списаний; после одного confirm одно выполнение; изменённые условия не исполняются по старому approval; источник не меняется скрыто; другой клиент не получает результаты; закрытие MAX не останавливает job.

**Готово:** готовый поисковый механизм из выверенной версии доступен обычному клиенту в миниаппе, с прежними разрешениями и историей.

Включить локальные улучшения получения/выполнения сообщения, сохранения следующего черновика, компактных фоновых задач и раскрытия длинного ответа. Scope change и отзыв прав очищают частные данные; transient refresh failure сохраняет прежний результат с ясным статусом.

**Проверки:** расширить существующие PlatformOutreach/Partnerships/Prepared/GroupLaunch тесты. Проверить настоящие headers MAX, двойное нажатие, смену бизнеса, ошибки, раскрытие условий и малый экран. Не менять правила отправки ради прохождения UI-теста.

**Готово:** найденные готовые функции не потеряны, обычный клиент получает недостающие действия через тот же контур.

### T6 — Интеграционные доказательства до выкладки

**Зависимости:** T1–T5.

**Основа проверок:** существующие `tests/test_operator_platform_outreach.py`, тесты continuation/search-routing/receipts/approval и компонентов PlatformOutreach/PreparedPartnershipMessages/PartnershipGroupLaunch из найденных веток. Добавить недостающее покрытие обычного клиента, общих источников и PostgreSQL к объединённой версии; отдельные новые файлы создавать только для этих новых сценариев.

Использовать настоящие Flask routes, настоящую тестовую PostgreSQL, существующий `process_chat`, approval и очередь. Подменять только внешние провайдеры. Тестовую БД проверять через проектные helpers; production DSN не использовать. Покрыть владельца, редактора, viewer и администратора, а не только superadmin-проход.

Проверить полный цикл: preview → prepare → confirm → worker → запись компаний → кампания/очередь → подтверждённый результат отправки → входящий ответ → остановка последующих касаний → reopen. Письмо/ответ на подменённом провайдере помечаются как локальные доказательства. Проверить narrow viewport, сборку и отсутствие новых TypeScript-ошибок; существующие падения оформить отдельно с точным влиянием на релиз.

**Готово:** все изменённые сценарии проходят интеграционно; приложен список покрытых и ещё не доказанных условий. Нет вывода «работает в production».

### T7 — Commit, выкладка кандидата и живой Riderra

**Зависимости:** T6 и восстановленное выполнение серверных команд.

1. Создать конкретный проверенный commit; отправить одинаковый SHA в GitHub и GitVerse, сверить remote refs без force-push.
2. Сохранить предыдущий пакет и env-настройки затронутых сервисов. Выкладывать manifest файлов и frontend dist, не весь грязный каталог.
3. Сначала ограниченный кандидат для Riderra. При изменении env пересоздать только затронутые контейнеры; restart сам по себе env не обновляет. Проверить Compose, логи, HTTP, исполняемые файлы/импорты и реально загруженный frontend bundle.
4. Через авторизованный MAX открыть существующий Riderra sender, выполнить свежую проверку ответов, показать условия небольшой согласованной подборки компаний и выполнить разрешённый ограниченный поиск.
5. Подготовить одно контрольное письмо с конкретным адресатом и применимым разрешением; проверить одно принятое провайдером отправление и сохранённый message ID. Не менять общие отправки клиентов ради теста: `pilot-dispatch-first-touch` применим только при уже выключенном глобальном диспетчере; иначе использовать обычный согласованный маршрут конкретной кампании.
6. Получить настоящий контрольный ответ, обновить через миниапп, проверить одно входящее событие и остановку нужных follow-up. Закрыть/открыть MAX и проверить сохранённую историю.
7. Зафиксировать ID задания/кампании/очереди/провайдера/входящего и времена. Затем проверить обычный клиентский аккаунт и разделение двух разрешённых областей, расширять включение по результату готовности.
8. При регрессии откатить пакет/целевые настройки до сохранённой версии, не удаляя выполненные отправки и полученные ответы. Изменение схемы — только отдельная подготовленная миграция.

**Готово:** полный цикл пройден на выложенном SHA, доказан обычный клиентский доступ, повтор не создаёт второй поиск/письмо. Доступ Gmail из чата разработки не засчитывается.

### T8 — Контент и настройка автоматизаций: следующий релиз

**Зависимости:** принятый T7.

Сначала проверить уже существующие контентные и compiled-сценарии; новые работы выделять только по обнаруженным разрывам. Применить тот же контракт scope/готовности/согласования/истории. В LocalOS доступны источник, правила, расписание, лимиты, результат, ошибка и остановка. Переиспользовать текущие agent versions, расписания и worker; не создавать второй исполнительный механизм. Точный manifest и тесты T8 составляются после приёмки аутрича, чтобы не увеличивать первый релиз до общего переписывания платформы.

## 6. Порядок и протокол исполнения

Основной порядок исправления разницы: **T0 (объединение/сверка) → T1 → T2 → T3 → T4 → T5 → T6 → T7**. Это не повторное внедрение готовых механизмов. T8 выполняется следующим релизом. Независимые локальные работы не ждут серверной части T0; живая сверка T0 обязательна перед T7.

После каждого этапа фиксировать в этом документе: status (`pending/in_progress/blocked/done`), commit/набор изменённых файлов, выполненные тесты и результат, оставшиеся ограничения. Переходить дальше только при выполнении указанного «Готово»; blocked-подпункты не считать выполненными.

Команда для начала исполнения: **«Выполняй технический план с T0»**. Уже выданные разрешения на commit/push/deploy сохраняются; новых внешних расходов и отправок сверх конкретных применимых условий этот документ не разрешает.
