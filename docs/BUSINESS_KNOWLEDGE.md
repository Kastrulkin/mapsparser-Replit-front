# Знания о бизнесе — реализация и выпуск

Статус: **реализовано и проверено; выпуск согласован 12.10.2026 и выполняется
после проверки резервных копий БД и закрытых документов**. Первое место
редактирования — «Бизнес и команда» → «Знания о бизнесе»:
`/dashboard/profile?section=knowledge`. MiniApp переиспользует эти же формы.

## Ответственность разделов

| Раздел | Что хранит |
|---|---|
| Знания о бизнесе | Постоянные характеристики, правила, особенности, документы |
| Рабочий журнал | События, предложения, наблюдения, временные ограничения и решения |
| Сегодня | Актуальные задачи и требующие человека решения |
| Результаты | Выполненную работу, материалы и подтверждения |

Количество кресел не означает доступность мастера или времени. Заполнение поля
не создаёт финансовые ресурсы и не считается выполненной рабочей задачей.

## Модель и права

Миграция `20261012_business_knowledge` добавляет определения/значения/правила/
документы, неизменяемую историю, отдельные назначения редакторов и квитанции
повторных запросов. Источник истины — PostgreSQL, не журнал и не поисковый индекс.
Идентификаторы сохраняются при переименовании и замене файла. Поля и варианты
выбора архивируются; совместимость заполненных значений проверяется до изменения
типа. Для пустого значения используются отдельные состояния `unknown`, `set`,
`not_applicable`; число 0 и `false` сохраняются как реальные значения.

Владелец меняет структуру, редакторов и аудиторию. Управляющий/admin получает
редактирование знаний только после назначения, без нового права на тариф или
команду. Участник читает доступные сведения и предлагает изменение через журнал.
Аудитории `team` и `management` фильтруются при чтении, истории, скачивании,
предложениях и подготовке контекста помощника. После отзыва назначения сервер
повторно проверяет право перед сохранением.

Сетевые определения и правила наследуются, правило точки может иметь местное
исключение. Физическая вместимость не наследуется. Суммы считают доступные точки
с совместимыми единицами и известным смыслом предложенного поля; указывают охват.
Максимальный размер группы не суммируется. Название пользовательского поля само
по себе не превращает его в показатель для расчётов.

Финансовый перечень показывается отдельно. Только явное подтверждение полноты
позволяет назвать его размер числом активных ресурсов. Сверка конкретного вида
ресурсов требует известных типов всех записей; иначе выводится объяснение.
Профиль, услуги/цены и сотрудники сохраняют свои исходные места редактирования.
Сверка финансовых ресурсов сохраняет действующий доступ к финансам; закрытые
записи не передаются через знания. Хранение самих характеристик доступно независимо
от тарифа.

## Справочник и наборы

Доступные типы читаются из того же `businesstypes`, что обслуживает
`/api/business-types`. Наборы — сопоставления существующих `type_key`, не второй
справочник типов. Есть школа, СТО, салон, кафе, транспорт и остальные действующие
типы; неизвестному типу предлагается универсальный набор. Сохранённые hotel и
guest_house доступны по их прежнему ключу и не переназначаются.

Резервный список профиля приведён к транспорту из серверного справочника;
сохранённые отсутствующие типы добавляются в список выбора отдельно. Применение
набора требует выбора полей, не создаёт дублей и не скрывает сетевые значения.
Дополнительный набор не меняет основной тип бизнеса.

## API

Все обращения: авторизация существующей сессией, `scope_type=business|network`
и `scope_id`. Ответы частные, без кеширования. Существующие endpoints сохранены.

| Запрос | Назначение |
|---|---|
| GET `/api/business-knowledge` | Раздел с учётом прав и наследования |
| GET `/api/business-knowledge/templates` | Наборы по действующему справочнику |
| POST `/api/business-knowledge` | `field`, `value`, `rule`, `archive`, `template`, `editor`, `inventory_complete` или проверка текста `document` |
| GET `/api/business-knowledge/{id}/history` | Версии доступной записи |
| POST `/api/business-knowledge/documents` | Закрытая загрузка или замена файла |
| GET `/api/business-knowledge/{id}/download` | Авторизованное скачивание; необязательный `version` |
| POST `/api/business-knowledge/preview` | Сравнение и существующее подтверждение Operator |
| POST `/api/business-knowledge/proposals` | Предложение участника в рабочий журнал |

Изменение передаёт `request_id`; существующая запись — также `id` и `version`.
Отставшая версия возвращает 409. Повтор одинакового запроса возвращает прежний
результат; повторное использование ключа для другого изменения отклоняется.
Сохранение сериализовано по контексту; определения дополнительно защищены от
одновременной смены типа и записи значения.

Прямые ссылки используют `field`, `rule` или `document`, а для Web — также
`business_id`/`scope_type`. MiniApp принимает разрешённый `item_id` выбранной
записи. `return_to` проходит существующую проверку внутренних маршрутов и ничего
не запускает. Ручная смена контекста очищает выбор и связь с наблюдением.

## Документы

PDF/DOCX/TXT: до 10 МБ, PDF до 50 страниц, извлечённый текст до 30 000 символов.
Проверяется полный извлечённый текст, без скрытого усечения; превышение требует
разделить файл. Используется существующий безопасный разбор документов, OCR нет.
Скан сохраняется как оригинал с состоянием `text_unavailable`; текст можно внести
вручную. Только проверенный и явно подтверждённый текст используется помощником.
Просроченные, неподтверждённые и архивные источники исключаются из контекста.

Оригиналы: `BUSINESS_KNOWLEDGE_DIR`, по умолчанию `/app/business_knowledge`;
имена UUID, файлы 0600, каталог 0700. Нет публичного URL и доступа через медиа.
Том `./data/business_knowledge` подключается к app, worker и telegram-bot;
operator-worker наследует том worker. Для закрытого каталога нужно назначить UID
и GID реального пользователя контейнера, а не создать root-каталог по умолчанию.
Повторный хеш открывает существующий документ; замена сохраняет новую версию и
прежний оригинал. `.gitignore` и существующий `.dockerignore` исключают файлы.

## Связи с работой

Предложение сотрудника остаётся существующей записью журнала со ссылкой на поле
или правило. Оно показывается редактору в знаниях. Просмотр не меняет факт.
Сохранение из наблюдения проверяет его контекст, цель и версию, показывает
«Было / Станет» и использует существующий `operatoractions`. Обычная запись
журнала сохраняет прежние правила доступа; узкое право предложения знаний не
открывает весь рабочий журнал.

Web и Telegram используют `knowledge.read`, `knowledge.prepare_change` и
`knowledge.propose_change`. Хранение знаний не получает тарифной блокировки;
обращение через чат сохраняет действующие ограничения чата.

Общий сервис разрешённых актуальных сведений подключён к новостям, контент-плану,
подготовке матрицы среднего чека, рабочим рекомендациям и контексту автоматизаций.
Источники содержат ID/версию, автора, дату и адресную ссылку. В матрице и
контент-плане источники сохраняются в существующих JSON-метаданных; у новости
возвращаются в результате поручения. При локальном fallback матрицы не заявляем
использование знаний, которых не было в расчёте.

Изменение использованного значения, определения, правила или документа требует
повторной подготовки связанного результата перед подтверждением автоматизации
или матрицы. Справочный текст не редактирует утверждённый compiled script и не
расширяет его разрешённые действия. Чистые compiled-программы продолжают получать
только явно заданные входы; знания используются на этапе подготовки контекста.
Новые глобальные задачи «заполнить все знания» в «Сегодня» не создаются. Запрос
конкретной работы может вернуться к ней через проверенный `return_to`.

## Проверки и ограничения приёмки

Целевые проверки: реальные временные схемы локального PostgreSQL, API, права,
версии и повторные запросы, одновременные сохранения, документы, наследование,
предложения и подтверждения Web/Telegram. React проверяет гонку контекста,
потерю доступа, временную ошибку, ссылку MiniApp и отдельное подтверждение.
Проверено: 29 серверных сценариев с локальным PostgreSQL, 77 проверок
совместимости и 19 тестов интерфейса. Проверки типов, обе сборки, product UI
guard и целостность сборок выполнены также для изолированного frontend.
Точные результаты и скриншоты находятся в локальном task bundle
`.agent/tasks/business-knowledge-20261012/`.

Браузер: 390/768/1280, заполненное и пустое состояние, длинные подписи, форма,
клавиатура и отсутствие переполнения. Это локальный стенд с тестовыми ответами,
не production-проверка. Исследование с пятью представителями аудитории
**не проведено**; результат 4/5 не заявляется. Production-сквозные проверки
выполняются только после отдельно согласованной выкладки.

## Выпуск и откат

Рабочая копия содержит посторонние изменения. Для ревью подготовлен task-only
patch к сохранённой исходной копии. Для сервера отдельно подготовлен patch к
прочитанным production-файлам, сохраняющий другие production-изменения. Полную
грязную папку `src/` и текущий `docker-compose.yml` переносить нельзя.
Исходники frontend на сервере отстают от опубликованного dist; это ожидаемо при
канонической частичной выкладке, но не подтверждает их совпадение с локальной
сборкой. Подготовлен отдельный frontend на зафиксированной Git-версии
`a89fd887ed0ed5c91c14cdcefaf6e2f22dc25b39`: изменения знаний и явный список
существующих зависимостей навигации, «Сегодня», «Результатов» и локализаций.
В релиз также включены прочитанные исходники действующих партнёрств, чтобы
не откатить опубликованные этапы аутрича и адресные переходы. Из несовместимостей
исходного набора исправлены объявления типов, свойства формы и добавлены
существующие переводы; новых внешних действий это не добавляет.
Список и контрольные суммы — `frontend-isolation.json`; дополнительные
фрагменты переводов — `isolation-locale-fragments.json`. Посторонняя рабочая
копия целиком в этот набор не переносится. Проверенные `dist` и `public-dist`,
исходный архив и patch к зафиксированной версии находятся в `release/`.
До публикации требуется отдельно согласовать этот состав и повторно проверить
production-хеши: patch сервера нельзя применять к изменившимся файлам вслепую.

После согласования выпуска, в именованной tmux-сессии; каждый серверный блок
начинается `cd /opt/seo-app`:

1. Повторить проверку hashes исходных файлов. Сохранить предыдущий dist,
   затрагиваемые серверные файлы, Compose, резервную копию PostgreSQL и приватных
   файлов. Проверить читаемость резервных копий; новые сведения не удалять.
2. Подготовить каталог через `scripts/prepare_business_knowledge_storage.sh`.
   Применить только проверенный серверный patch, новые модули и одну миграцию.
3. Выполнить целевое `flask --app src/main.py db upgrade 20261012_business_knowledge` в app. Родитель
   этой миграции — `20261009_business_chat`; не выполнять локальное `upgrade heads`:
   в рабочей копии есть посторонняя ветка миграций типов бизнеса.
4. Для подключения нового тома требуется пересоздать **только** app, worker,
   operator-worker и telegram-bot с проверенной конфигурацией (`up -d --no-build`),
   а не ограничиться restart. Образ и БД не пересобираются. Проверить владельца и
   запись в каталоге из контейнера, не публикуя тестовый файл как документ.
5. Собрать frontend из изолированного согласованного набора; выпускать через
   [канонический frontend runbook](FRONTEND_DEPLOY_RUNBOOK.md), сохраняя старые
   lazy assets. Для серверной части соблюдать
   [Docker/Postgres runbook](DOCKER_DEPLOY.md) и сверять `/app/src/...`.
6. В порядке проекта: `docker compose ps`, свежие app-логи, ответ localhost:8000,
   затем адресные API/браузерные проверки. Проверить права сотрудника/редактора,
   сеть → точку, документы, смену контекста, подтверждение и Telegram.

Откат возвращает предыдущие исходники/сборку. Том, новые записи и история
сохраняются. `downgrade()` намеренно не удаляет таблицы; откат приложения не
является удалением пользовательских данных. Нет автоматического удаления
старых документов или восстановления БД поверх новых сведений.
