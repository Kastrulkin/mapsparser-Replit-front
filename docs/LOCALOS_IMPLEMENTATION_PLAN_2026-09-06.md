# LocalOS: план следующего этапа после архитектурного разбора

Дата: 6 сентября 2026. Статус: **реализация и локальная проверка в работе**. Фактические результаты и незакрытые условия ведутся в [отчёте реализации](LOCALOS_IMPLEMENTATION_STATUS_2026-09-06.md).

Это актуальный порядок оставшихся работ из [плана 5 сентября](LOCALOS_IMPLEMENTATION_PLAN_2026-09-05.md), уточнённый после чтения кода на коммите `ffc54c19`. Уже выпущенные изменения описаны в [отчёте о выпуске](LOCALOS_RELEASE_2026-09-05.md). Новый документ не объявляет прежний план завершённым и не повторяет реализованные пункты.

## 1. Исходное состояние и результат

Уже есть: прямое меню, постоянная главная «Сегодня», scoped preferences, Operator leases, immutable compiled artifacts, проверка примеров и отдельный runner. Первый production-выпуск и четыре миграции завершены. По его проверке compiled preview/execute, сбор активности и предложения смены приоритета выключены; перед следующим выпуском фактические флаги нужно сверить заново.

Остаются: четыре кандидата на ошибки состояния/повтора, нетехнический редактор скрипта, доступ к разрешённым источникам, короткие транзакции agent runs, применение UnitOfWork в реальном сценарии, перенос runtime DDL, завершение доменной декомпозиции и проверка персонализации на использовании.

Целевой результат:

- Пользователь сразу видит актуальную работу по своему направлению и понимает следующий шаг.
- Смена бизнес-контекста и потеря доступа не оставляют на экране чужие или недоступные данные.
- Пользователь описывает формальную задачу, проверяет программу на примерах, утверждает версию и повторно запускает её без модели.
- Повтор запроса после сбоя и новый намеренный запуск имеют разную семантику.
- Внешние действия проходят существующую границу ActionOrchestrator и подтверждения.
- Выполнение длительной работы не удерживает транзакцию БД на время ожидания провайдера.

Сохраняем Flask/PostgreSQL, существующие blueprints/versions/runs, Operator и prospectingleads. Целевая архитектура — модульный монолит с отдельными исполнителями. Новый универсальный оркестратор, новая CRM и массовая перепись backend в этот план не входят.

## 2. Выпуски и зависимости

Размер S/M/L означает относительную сложность, а не обещание календарного срока. Оценка уточняется после воспроизведений и инвентаризации R0.

| Выпуск | Проверяемый результат | Зависимость | Размер |
| --- | --- | --- | --- |
| R0 | Зафиксированы контракты, границы и исходные показатели | Начало реализации | S |
| R1 | Корректные ошибки доступа, смена приоритета и повтор запуска | R0 | S–M |
| R2 | «Сегодня» ведёт контентного, influencer и automation пользователя к работе | R1 | M |
| R3 | Явный admission/UoW, короткие транзакции и fenced agent queue | R0; R1 для общего HTTP-контракта | L |
| R4 | Законченный compiled-сценарий «проверить таблицу → получить отчёт» | Контракт после R0; UI после R1; рабочий пилот после R3 | L |
| R5 | Проверенные сигналы и предложения приоритета по согласию | R1, R2 и период наблюдения | M |
| R6 | Runtime DDL перенесён, домены разделены, миграционные права отделены | Инвентаризация после R0; переносы параллельно R3/R4; права только после полного охвата | L |
| R7 | Предложения внешних действий, второй script-пилот и поштучный перенос legacy | Успешный read-only пилот R4 и необходимые границы R3/R6 | L |

R2 и backend R3 можно вести параллельно после R1. Спецификацию и интерфейс R4 можно готовить до окончания R3, но рабочее исполнение включать только после проверки очереди. Инвентаризация и отдельные переносы R6 не должны ждать завершения всей продуктовой ветки.

## 4. R1 — состояние, доступ и повтор

**Файлы:** `frontend/src/lib/auth_new.ts`, `frontend/src/pages/dashboard/TodayPage.tsx`, `frontend/src/components/agents/CompiledScriptBuilder.tsx`; при необходимости DTO и узкие API-контракты в `src/api/operator_api.py` / `src/api/agent_blueprints_api.py`.

| Кандидат | Изменение после подтверждения | Приёмочный сценарий |
| --- | --- | --- |
| Старый обзор сохраняется после отзыва доступа | Типизированная ошибка со status/code; сохранять обзор при временном сбое, очищать при 403/404 недоступного scope | Успешная загрузка → 403: данные и действия исчезли; успешная загрузка → 503: прежний обзор с предупреждением и повтором |
| Выбранный приоритет расходится с содержимым | После успешного решения получить и применить актуальный scoped overview; не переставлять фоновые обновления без действия пользователя | Выбор «Инфлюенсеры» обновляет сравнимые задачи сразу; срочная задача остаётся первой |
| Отклонённое предложение остаётся на экране | Различать отсутствующее поле и явное `priority_proposal: null` | Accept/decline/snooze/opt-out убирают старую карточку; новый ответ не возвращает её через fallback |
| Новый запуск повторно использует прежний ключ | Отдельные намерения «повторить запрос» и «запустить ещё раз»; UI после принятия показывает состояние и результат | Timeout + retry возвращает тот же run; новый намеренный запуск с теми же данными создаёт новый run; двойной клик не дублирует работу |

Общий HTTP-клиент должен сохранить совместимость `.message` и действующее поведение истечения сессии. Нельзя одновременно переписывать все существующие callers. Проверить запрос без JSON, сетевой обрыв и прикладной 409.

**Дополнительные переходы:** A→B при незавершённом запросе A; смена пользователя/сети; поздний ответ сохранения предпочтения; одновременное изменение в двух вкладках. Ответ для прежнего scope не обновляет новый экран, 409 не выглядит как успешное сохранение.

**Проверки:** расширить `TodayPage.test.tsx`, `CompiledScriptBuilder.test.tsx`, добавить узкий тест HTTP-клиента; использовать `tests/test_operator_today_api.py` и `tests/test_agent_blueprint_async_contracts.py` для серверных контрактов. Сначала красное воспроизведение, затем минимальное исправление и тот же зелёный тест. Если гипотеза не подтверждается — зафиксировать это и исключить ненужную правку.

**Выпуск/откат:** небольшой самостоятельный web/API выпуск; обычно без миграций. Возврат предыдущего frontend/API не должен менять сохранённые предпочтения и историю запусков.

## 5. R2 — законченный UX главной и рабочих направлений

**Пользователи:** владелец/менеджер, который ведёт контент; специалист по коллаборациям; владелец с работающей автоматизацией. **Задача экрана:** показать важную работу и довести до следующего результата.

**Файлы:** `TodayPage.tsx`, `DashboardSidebar.tsx`, `DashboardLayout.tsx`, существующие компоненты dashboard, локализация и `src/services/today_workspace.py`.

1. Сохранить «Сегодня» постоянной главной и прямые ссылки разделов. «Пути роста» остаются дополнительным знакомством с возможностями.
2. Зафиксировать порядок: срочное → один главный следующий шаг → продолжить работу → результаты. Аналитика и дополнительные сведения располагаются ниже или раскрываются отдельно.
3. Переименовать настройку в «Что показывать первым на “Сегодня”». После выбора сразу показать изменённое содержание, а не только новое название предпочтения.
4. Контентный сценарий: ближайшая публикация/черновик/продолжение плана и ссылка на все материалы. Influencer-сценарий: ответ, кандидат на согласование, следующий этап сотрудничества. Автоматизация: результат, ошибка или запрос решения; здоровая работа не требует лишних кликов.
5. Если по выбранному направлению нет задач — показать полезный старт этого направления. Не создавать фиктивную работу и не оставлять экран без понятного действия.
6. Сохранить точный переход к материалу, сотрудничеству или запуску. Для сетевой задачи корректно выбрать её локацию. Повторное открытие общего реестра вместо выбранного объекта не считается завершённым сценарием.
7. Проверить design tokens, hit area, focus, клавиатуру, длинные переводы, загрузку/пустой экран/частичный сбой и ширины 360, 768, 1280px. JSON, source и технические статусы остаются во втором слое.

**Приёмка:** контент, коллаборация и автоматизация доступны из главной одним явным действием; срочность выше предпочтения; смена приоритета не меняет меню и явные deep links. В первом качественном тесте минимум 4 из 5 представителей целевой аудитории без подсказки находят следующее действие за 30 секунд. Это критерий небольшого UX-пилота, не статистическое доказательство для всей аудитории.

**Проверки:** точные браузерные сценарии со staging API, минимум один переход с отказом/устаревшими данными на каждый поток; отдельно контентный, influencer и partnership сценарий до результата. Обновить существующую UX-документацию после проверки.

## 6. R3 — транзакции, очереди и отдельные исполнители

### R3.1. Первый реальный UnitOfWork

Начать с **постановки agent run**: общий application service для обычного и compiled запуска. Переиспользовать `enqueue_agent_run(cursor, ...)`, не создавать второй механизм очереди.

**Файлы:** `src/core/unit_of_work.py`, `src/api/agent_blueprints_api.py`, `src/services/agent_run_queue.py`; новый узкий admission service — планируемый файл. Доступ проверяется через полный AuthContext, а не только user_id.

Одна команда атомарно сохраняет run, резервирование и необходимые записи аудита. Внешняя сеть не вызывается под открытой транзакцией; если preflight требует внешнего наблюдения, получать его отдельно, затем повторно проверять изменяемые права/версию при admission.

**Приёмка:** инъекция ошибки между сохранениями оставляет ноль частичных записей; запрещённый scope даёт ноль записей; повтор ключа не резервирует стоимость повторно. `DatabaseManager.close()` глобально пока не менять. После успешного пилота вести явный список оставшихся callers и переносить их по сценариям.

### R3.2. Короткое выполнение agent runs

**Файлы:** `src/services/agent_run_queue.py`, `src/services/agent_blueprint_runner.py`, `src/worker.py`, новая расширяющая Alembic-миграция после фактического head.

Разделить получение задания, чтение входов, внешний вызов, запись шага и завершение. Добавить lease/attempt token для `agent_runs`, heartbeat отдельным соединением и conditional finalization. Существующие Operator leases использовать как образец протокола; `operator_async_jobs` и `agent_runs` не объединять.

**Приёмка:**

- Во время задержанного ответа провайдера нет удерживаемой run-транзакции/блокировки строки.
- Два worker не завершают одно владение; старая попытка после потери lease не записывает результат и не резервирует/списывает повторно.
- Kill до/после получения задания, истечение lease и превышение max attempts дают ожидаемое восстановление.
- Завершённые шаги и история сохранены; retry не повторяет уже подтверждённый внешний эффект.
- Успевший уйти внешний запрос нельзя «отменить» одним fencing token. Неизвестный исход проходит сверку с провайдером либо ручное решение; автоматический слепой повтор запрещён.

Проверки — реальный изолированный PostgreSQL, два соединения/worker и управляемый fake provider, не только mock cursor. Расширить `test_runtime_queue_pg.py`, `test_agent_blueprint_async_contracts.py`, `test_application_boundaries.py`; соседний Operator lease suite сохраняется зелёным.

### R3.3. Разделение worker по ролям

Использовать существующий `docker-compose.workers.yml`. До включения составить таблицу владельцев всех циклов: parser, agent, operator, dispatcher, maintenance/scheduler. Каждую очередь и расписание обслуживает ровно назначенная роль; прежний all-worker не должен дублировать выделенные циклы.

**Приёмка:** остановка agent-worker не останавливает parser/Operator; задания восстанавливаются без дублей; расписание принимается однократно. Вводить ограничения параллелизма по бизнесу и провайдеру там, где возможны внешние вызовы.

**Передача владения и откат:** остановить новое admission и приём расписаний; дождаться завершения текущих agent leases либо их контролируемого истечения; остановить прежних потребителей; только затем включать нового владельца. При возврате к all-worker сначала остановить выделенные agent/scheduler роли. При выделении ролей сначала отключить соответствующие циклы all-worker. Если внешний вызов остался с неизвестным исходом, применить сверку из R3.2 до повторного эффекта. Новые колонки и журнал не удалять.

## 7. R4 — первый полноценный compiled-сценарий

**Первый продуктовый сценарий:** «Проверить таблицу по утверждённым правилам и получить отчёт об ошибках». Начать с CSV или вставленной таблицы. XLSX и Google Sheets — следующие источники после первого проверенного пути, без обязательной зависимости пилота от OAuth.

### R4.1. Проверяемый контракт

Переиспользовать pilot kind `localos.sheet_validate_dedupe_report.v1`, существующие source/manifest/fixtures и независимую проверку результата. Сохранить настоящий генерируемый Python; эталонная проверка не заменяет пользовательскую программу фиксированной функцией.

Зафиксировать единственную каноническую форму входа, правила сопоставления колонок, пустых значений, типов и дублей, допустимые лимиты и формат отчёта. Изменение контракта требует совместимой версии, а не незаметной смены смысла старого артефакта.

Примеры: обычная таблица, отсутствующее обязательное поле, дубликат, некорректная строка, пустой источник и граничный размер. Хотя бы один ожидаемый результат задаёт пользователь независимо от генератора. Неформальные критерии уточняются до генерации; задачи, требующие нового суждения LLM при каждом запуске, не называются compiled.

В approval входят source, manifest/schema, разрешённые операции/источники, правила, fixtures, runtime/SDK version и проверочный digest. Новые данные запуска не требуют генерации заново; изменение правил, схемы или полномочий создаёт новый candidate.

**Файлы:** `compiled_script_artifact.py`, `compiled_script_runtime.py`, `compiled_json_schema.py`, compiled routes в `agent_blueprints_api.py`, существующие compiled API/artifact tests.

### R4.2. Разрешённые снимки данных и read-only SDK

Данные получает приложение через ограниченный gateway, а runner получает подготовленный вход. Сначала — пользовательская таблица, затем один зарегистрированный read-only источник LocalOS.

Планируемый snapshot service проверяет пользователя, бизнес, источник, роль и лимиты. В run фиксируются snapshot ID/hash, схема и происхождение. Секреты и подключения разрешаются gateway; они не входят в исходник, fixtures, runner environment или отчёт. Срок хранения и доступ к снимкам определить до пилота; не записывать целую таблицу в обычные логи.

**Приёмка:** чужой source ID недоступен; смена исходной таблицы не меняет вход уже принятого run; повтор с тем же snapshot и артефактом даёт тот же канонический отчёт. SDK allowlist проверяет и внутренние зависимости: скрытого runtime LLM быть не должно.

### R4.3. Нетехнический конструктор и жизненный цикл

Путь: выбрать таблицу → сопоставить колонки → описать правила → проверить примеры → увидеть строки с причинами ошибок → подтвердить именованную версию → запустить другую таблицу → открыть/скачать отчёт.

**Файлы:** `CompiledScriptBuilder.tsx`, `AgentBlueprintsPage.tsx`, существующие компоненты и API загрузки/истории. Новые сервисы/DTO добавлять только для отсутствующих функций; первичный экран не требует JSON.

Состояния программы: черновик, проверяется, требует исправления, готова к утверждению, утверждена/включена, приостановлена, заменена. Ошибка сообщает конкретный следующий шаг. Редактирование сохраняет текущую рабочую версию до отдельного утверждения кандидата; запуск и повтор ведут к одному журналу.

**Приёмка:** владелец проходит пример без JSON/кода; отчёт показывает исходные номера строк и причины; повторный запуск не вызывает компилятор; изменение примера/правил инвалидирует только соответствующий candidate/approval.

### R4.4. Изоляция и ограниченное включение

Сохранить отдельный runner без DB/provider credentials, host filesystem и Docker socket. Проверить закреплённый образ, HMAC, ограничения CPU/RAM/PID/time/output, сетевую изоляцию, обработку повреждённых запросов, таймаут чтения и очереди. AST-проверка — дополнительный слой, а не самостоятельная граница защиты.

Заменять последовательный сервер ограниченным пулом только с явным лимитом нагрузки и проверкой изоляции каждого выполнения; простое снятие ограничения параллелизма не подходит. До общей многопользовательской эксплуатации необходим отдельный обзор угроз выбранного sandbox.

**Включение:** добавить backend-проверяемый допуск бизнесов к пилоту; preview в одном внутреннем бизнесе → ручное read-only исполнение там же → небольшая согласованная группа. Первичный smoke включает 10 preview и 5 запусков плюс отрицательные и crash-сценарии; это минимальный smoke, не доказательство надёжности по статистике. Расписания и внешние записи в первом пилоте выключены.

**Приёмка:** `runtime_ai_calls=0` подтверждено наблюдением зависимостей/сетевых вызовов, а не только полем ответа; внешних эффектов нет; подмена hash/image/approval блокирует запуск; недопущенный бизнес заблокирован; выключение execute действует в API, общей очереди и worker.

**Откат:** выключить execute/допуск новых запусков, затем preview; не удалять версии, snapshots и историю. Для ещё не начатых заданий фиксировать явное состояние; после включения требуется осознанный повтор. Уже выполняемый запрос учитывать отдельно.

## 8. R5 — персонализация по согласию

**Файлы:** `today_preferences_service.py`, `product_telemetry_service.py`, `today_workspace.py`, Today UI и существующая обработка подтверждённых действий.

1. Сначала проверить семантику событий и dedup на тестах, затем включить только сбор для пилота; предложения оставить выключенными.
2. Разделять завершённые пользовательские действия, активные процессы, просмотры и фоновую работу. Исправная автоматизация может быть важна при редких посещениях; частота контентных действий и поиска партнёров несопоставима без нормализации.
3. Ручной выбор имеет приоритет. Нельзя считать фоновое выполнение, demo, impersonation или административные просмотры доказательством нового интереса пользователя.
4. Снять минимум полный 14-дневный цикл существующей гипотезы; при недостаточных данных продолжать наблюдение, а не автоматически включать предложения. Проверить уместность выборки предложений вручную с пользователями.
5. Зафиксировать веса, minimum evidence, cooldown и объяснение предложения. Существующие «3 дня / 5 действий / 60%» не считать доказанными порогами.
6. Включить предложения для пилота отдельно от сбора. Сохранить accept, decline, snooze, opt-out и undo. Молчание не означает согласие; порядок меню не меняется.

**Приёмка:** каждый предложенный переход объясним конкретными разрешёнными сигналами; до согласия `primary_flow` не меняется; фоновые запуски не вытесняют ручной выбор; отказ/отсрочка соблюдают cooldown. Показатели: уместность, принятия/отказы, быстрые отмены и достижение результата. Не оптимизировать систему только на число кликов или accept rate.

## 9. R6 — завершение backend-переносов и качества

### R6.1. Runtime DDL и права

Дополнить существующую инвентаризацию всеми активными callers. Первый небольшой перенос: content plans / usernews bootstrap и `ai_learning`; далее ActionOrchestrator, card automation, growth и прочие найденные активные пути. Наличие определения функции само по себе не доказывает runtime-вызов — требуется карта callers и schema parity.

Каждый перенос: сравнить таблицы/колонки/индексы/defaults/constraints → Alembic → upgrade на существующем состоянии и с нуля → убрать bootstrap конкретного сценария → проверить тот же сценарий с запрещённым DDL.

Глобально отзывать DDL у app/worker можно **только после переноса всех их активных startup/request/job путей**, не после успеха одного пилота. Затем отдельный migrator выполняет upgrade под существующим advisory lock, а обычный старт только проверяет совместимость схемы.

**Порядок переключения:** сначала выпустить отдельную команду migrator и совместимый режим старта без auto-upgrade, сохранив работоспособность текущего выпуска. Затем migrator с DDL-ролью применяет миграции и подтверждает head; только после этого запускать app/worker с DML-ролью и отключённым auto-upgrade. До отзыва прав подготовить и проверить версию для отката, которая тоже умеет стартовать без auto-upgrade. Нельзя сначала отозвать DDL, оставив прежний `entrypoint.sh`, или автоматически возвращать широкие права ради отката.

**Файлы:** `src/services/content_plan_service.py`, `src/core/ai_learning.py`, далее перечисленные домены; Alembic; `entrypoint.sh` и compose только на этапе смены миграционного запуска. Новые schema/data изменения — с backup и процедурой по AGENTS.md; никаких runtime ALTER как обхода миграции.

**Приёмка:** эквивалентность схемы; endpoint/job не испускает DDL; обычные app/worker не могут CREATE/ALTER/DROP, а migrator может достичь ожидаемой ревизии; restart приложения не запускает upgrade. Старые данные не теряются, откат не удаляет новые таблицы автоматически.

### R6.2. Доменная декомпозиция и проверки

Использовать границу R3.1 как образец: transport → application command → domain/repository → adapters. Следующие законченные сценарии: review/approval, контент, партнёрства, финансы. Выделение файла считается результатом только после устранения соответствующих globals/обратных зависимостей и внедрения зависимости через явный интерфейс.

Поддерживать реестр оставшихся implicit commit callers, runtime DDL и transport-зависимостей. Завершать перевод по доменам; только после проверки всех зависимых callers менять глобальную семантику legacy close().

Сокращать TypeScript baseline отдельными проверяемыми изменениями; итоговый критерий — полный typecheck без baseline-исключений. Добавить проверку согласованности release commit, migrations, backend и frontend в автоматизацию выпуска. Проверки на mock API дополняются staging browser flow, а SQL/fencing — реальным PostgreSQL.

**Приёмка:** по каждому перенесённому домену есть список входных команд/запросов, одна ясная транзакционная граница, отдельные provider adapters и контрактные тесты; прежние API, тарифы и tenant boundaries сохранены. Полный backend-перенос не закрывается одной внедрённой UoW-командой.

## 10. R7 — внешние предложения и перенос старых автоматизаций

После read-only пилота программа может формировать типизированный план предлагаемых действий. Его создание не означает исполнение. ActionOrchestrator повторно проверяет capability, tenant, актуальные права, лимиты, idempotency и подтверждение точного содержимого.

Утверждение программы не заменяет подтверждение отправки/публикации/платежа. Для пакетного согласования закрепить содержимое, адресата, отправителя, канал, срок/время и лимиты; существенное изменение требует нового решения. Неизвестный результат провайдера означает сверку, а не безусловный повтор.

Второй пилот — формальная проверка карточки/полноты услуг с разрешённым чтением и отчётом. Затем сопоставлять каждый legacy-сценарий на fixtures и dry-run. Runtime AI-шаги не переименовывать в compiled; миграция заканчивается пользовательским утверждением новой версии. Два executor не должны выполнять одну логическую задачу.

**Приёмка:** подготовка плана не вызывает внешний эффект; изменённое подтверждение отклоняется; при неопределённом исходе нет дубля; rollback версии проверяет текущие права/runtime; история прежних запусков доступна.

## 11. Общие условия выпуска

- Для каждого выпуска: минимальный дифф → целевые проверки → совместимые backend/frontend сборки → staging API/browser → commit/push → согласованный production-выпуск → проверка живых файлов и поведения.
- Production-порядок: `docker compose ps` → свежие app logs → HTTP health → целевые endpoints. Серверные команды из `/opt/seo-app`, длительные операции в tmux; частичный deploy затронутых сервисов по AGENTS.md.
- Миграции расширяющие, с проверенной резервной копией и сверкой текущего head. Номера новых ревизий назначаются при реализации, а не предполагаются по старому snapshot.
- Проверять настоящие права business/network/demo/тарифов. Разрушающие сценарии, отказ провайдера, kill worker и конкуренция — на изолированной среде.
- При росте ошибок доступа, повторных эффектах или нарушении версии/approval прекращать новое admission соответствующего пилота и разбирать исход. Откат кода не должен терять новые данные и историю.
- Приложить commit, manifests, миграцию, состояние флагов, результаты проверок и ограничения. Проход сборки сам по себе не закрывает пользовательскую приёмку.

## 12. Что выполнять первым

Первый самостоятельный пакет — **R0 + R1**, затем R2 и R3 параллельно. Одновременно можно заморозить контракт R4.1 и начать инвентаризацию R6. Первый запуск compiled у пользователя — только после R3 и всех проверок R4. Персонализацию включать по готовности evidence, а не по дате окончания разработки.

План закрыт полностью только после проверок R1–R7 и документированного решения по каждому переносу legacy. Реализация ведётся по этому плану. Статус конкретных проверок, выпуска и production указан в отдельном отчёте; наличие кода не означает завершение пользовательского пилота.
