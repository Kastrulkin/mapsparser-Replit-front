## Резервная копия и область миграции

На сервере `/opt/seo-app/backups/max-20261015/` сохранены полная схема PostgreSQL (`schema-before.dump`) и данные всех изменяемых существующих таблиц (`affected-data-before.dump`: product_analytics_events, botfeaturerequests, alembic_version). SHA-256 — `migration-backup.sha256`, права архивов 0600. Схема и данные действительно восстановлены в отдельном временном PostgreSQL 16, без сети и production-томов, с ограничением памяти/CPU; результат `MIGRATION_BACKUP_RESTORE_OK`. Восстановленная версия — `20261012_business_knowledge`, контрольные количества — 128 analytics events, 1 feature request. Временный restore-контейнер удалён после проверки.

Это целевая копия для отката добавочной миграции, **не полный снимок всех бизнес-данных**. Попытка полного pg_dump остановлена до заполнения диска: таблица векторов не помещалась в безопасный запас. Незавершённый архив удалён; существующие резервные копии не удалялись. Перенос production-базы на локальную машину не выполнялся. Все production-данные остались на сервере.

Миграция создаёт MAX identities/preferences/inbox/dialogue state/buttons и добавляет MAX-поле в feature requests/каналы аналитики. Объекты бизнеса, услуги, продажи, кампании и кредиты миграция не изменяет. Текущие значения канала аналитики до миграции: web, telegram_mini_app. Используется явная цель `20261015_max_control` от `20261012_business_knowledge`; чужая Alembic-ветка не объединяется. Ожидание блокировок ограничено 5 с, statement — 120 с.

## Выкладка и откат

Команда выпуска запущена в серверном tmux `max-deploy-20261015`, журнал `/opt/seo-app/backups-max-deploy-20261015.log`. Перед заменой сохранены `code-before.tgz` и `frontend-before.tgz`; применяются только runtime-manifest и собранные assets. Старые frontend-assets сохраняются для открытых вкладок. В существующий Compose добавляются только MAX environment defaults; MAX_ENABLED/MAX_PUBLISH_ENABLED выключены по умолчанию. Перезапускаются app, worker, operator-worker и telegram-bot.

Откат приложения: выключить MAX, восстановить конкретные файлы из code-before/frontend-before, перезапустить затронутые сервисы. Новые таблицы и receipts не удалять автоматически. Восстановление данных из целевых архивов — отдельная ручная операция с проверкой изменений после backup; не восстанавливать старые данные поверх новых вслепую.
