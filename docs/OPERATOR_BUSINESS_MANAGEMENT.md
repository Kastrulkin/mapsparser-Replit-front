# Настройки бизнеса и сотрудники через Оператора

Статус: `beta`, реализовано и проверяется локально. Production rollout требует
отдельного согласования, backup PostgreSQL и Alembic-миграции
`20261009_business_chat`. Этот документ не подтверждает production-выкладку.

## Пользовательский сценарий

Владелец пишет поручение, получает старые и новые значения для каждого бизнеса,
уточняет неоднозначные сведения и подтверждает точное изменение. Web и Telegram
используют общий `route_operator_message`. Изменения профиля применяются только
в LocalOS; внешние карты не обновляются.

Примеры:

- «Измени адрес бизнеса на Москва, Ленина, 10 и сайт на example.ru».
- «Мы переехали в Дубай, обнови город и часовой пояс».
- Список `название бизнеса: новый часовой пояс/город` и команда «Проставь часовые пояса».
- «Добавь Анну, anna@example.ru, мастером в этот бизнес и отправь приглашение».

Упоминание `использован UTC` в предупреждении не является новым значением.
Москва, Дубай и Орхус в исходном сообщении дают `Europe/Moscow`, `Asia/Dubai`
и `Europe/Copenhagen`. Это именованные зоны, а не фиксированные сезонные смещения.

## Реестр и границы покрытия

Source of truth: [`business_settings_registry.py`](../src/services/business_settings_registry.py).
Реестр задаёт ключи, названия, синонимы, лимиты, зависимости, права и JSON-схему.
Новые поля профиля добавляются в реестр и persistence mapping; отдельный набор
фраз для каждого нового поля не нужен. Новое поле автоматически появляется
в дополнительных настройках формы.

| Настройка / действие | Статус | Граница |
| --- | --- | --- |
| Название, тип бизнеса, адрес, город, сайт, график | `beta` | Общая проверка и сохранение для формы `/api/client-info` и подтверждений чата |
| Валюта, часовой пояс | `beta` | Существующий versioned `finance_daily` apply; общий профиль бизнеса |
| Контактное лицо, телефон, email бизнеса | `beta` | `businessprofiles`; личный аккаунт владельца не изменяется |
| Несколько бизнесов | `beta` | До 20 явно выбранных объектов; владельческие права на каждый; одно атомарное подтверждение |
| Список пользователей | `beta` | Владелец, прямые сотрудники, сотрудники и владелец сети; один человек показывается один раз |
| Добавление аккаунта / изменение роли | `beta` | Только владелец бизнеса или сети; конкретные бизнесы либо явно выбранная сеть |
| Приглашение по email | `beta` | Отдельно подтверждённая отправка; состояние доступа и доставки раздельны |
| Ссылки на карты | `available` | Существующая ручная форма; общий чат-handler для этого списка в данной версии отсутствует |
| Контент-правила и передача материалов | `available` | Существующие специализированные tools, вне profile patch |
| Секреты подключений, смена владельца, системный superadmin, тариф | `gap` для общего profile patch | Не принимаются как произвольные поля; остаются существующие специализированные процедуры |
| Отзыв доступа / удаление пользователя | `gap` в новом handler | Не реализованы данным изменением |

Наличие настройки в продукте не означает возможность изменить её через любой
чат-handler. Неподдерживаемые поля возвращают уточнение/ошибку, а не успех.

## Права сотрудников

Source of truth: [`business_permissions.py`](../src/services/business_permissions.py).

| Роль | Разрешения |
| --- | --- |
| Владелец бизнеса или сети | Просмотр, операционная работа, настройки, сотрудники |
| Администратор (`admin`) | Просмотр и операционная работа в назначенной области; собственные рабочие сведения |
| Мастер (`master`) | Просмотр как у наблюдателя и собственные рабочие сведения; без общих operational writes |
| Наблюдатель (`viewer`) | Просмотр |
| Legacy `manager`, `member` | Существующие операционные права сохранены; не переименованы в мастера |

Рабочие сведения доступны только там, где включён существующий рабочий журнал.
Мастер не получает автоматически чужие визиты: сохраняется существующая
привязка сотрудника к мастеру и визитам. В этой версии просмотр не ограничен
только карточкой конкретного мастера; используется действующая read-модель бизнеса.
Доступы нескольких активных memberships объединяются; более широкая роль через
сеть не отменяется узкой прямой ролью.

## Защищённое выполнение

Tools: `settings.get_profile`, `settings.list_businesses`,
`settings.prepare_changes`, `settings.list_users`, `settings.prepare_user`.
Backend capabilities: `business.settings.apply_operator`,
`business.team.apply_operator`. Обе всегда требуют human review в
[`action_policy.py`](../src/core/action_policy.py).

Apply повторно проверяет активность пользователя, владельческие права,
область доступа и fingerprint исходных данных. Все настройки batch проверяются
перед первой записью. Advisory locks и `business_change_receipts` предотвращают
повторное применение одного подтверждения. Прежние координаты очищаются после
смены адреса/города; новую точку надо проверить на карте. `site` и `website`
сохраняются согласованно.

Новый сотрудник получает отдельный аккаунт. Заблокированный аккаунт не
активируется, роль владельца не меняется. Invitation receipt создаётся в одной
транзакции с membership, отправка выполняется после commit. SMTP attempt
claim предотвращает повторную отправку при повторном подтверждении. `sent`
означает принятие письма SMTP-сервером, не чтение или доставку в inbox.
При crash после claim состояние `sending` означает неизвестный результат;
автоматическая повторная отправка не выполняется. В этой версии отдельный
фоновой delivery recovery и отдельная кнопка retry не реализованы.

API формы: `GET/POST /api/operator/business-management`,
`GET /api/operator/business-members`; подтверждение использует существующий
`POST /api/operator/actions/<action_id>/confirm`.

## Проверка и rollout

Regression checks: [`test_business_chat_management_pg.py`](../tests/test_business_chat_management_pg.py),
[`test_business_settings_registry.py`](../tests/test_business_settings_registry.py),
[`BusinessChangeForm.test.tsx`](../frontend/src/components/dashboard/BusinessChangeForm.test.tsx),
[`profile-business-users.spec.ts`](../frontend/e2e/profile-business-users.spec.ts).
PostgreSQL-тесты используют только `OPERATOR_VOICE_TEST_DSN` отдельной тестовой БД.

До production: согласовать выкладку и schema change, создать и проверить backup,
применить миграцию по текущей Alembic-линии, выложить только связанные файлы,
перезапустить затронутые сервисы и проверить живые `/app/src/...`.
После этого проверить пользователя в профиле и исходную команду сначала до
preview. Изменение production-данных требует отдельного явного поручения.
