# Тест уведомления о клиентском диалоге — 30.10.2026

## Разрешённый режим

Пользователь уточнил: уведомлять **его для теста**, а не реальных сотрудников «Расчёски». Добавлен ручной self-only pilot. Нет автоматического фонового уведомления, выбора произвольного получателя или подписки сотрудников. Автоответы не включаются.

Доступен только внутренний диалог с client_phone, начинающимся на test-handoff:, в waiting_for_staff. Нужен operations.write на бизнес. Адресат — исключительно авторизованный пользователь, его активный аккаунт и положительный личный telegram_id из telegramcontrolpreferences. Телефон клиента, переписка и медицинские данные не отправляются. Сообщение содержит название бизнеса, явную отметку теста и предложение принять обращение.

## Переиспользование

Проверен живой get_openclaw_capability_catalog: available, в опубликованных действиях browser.read_page и partners.research_website. Для данного уведомления переиспользован готовый `services/telegram_bot_sender.py`, который уже доставляет уведомления owner-бота LocalOS. Новый внешний коннектор не создаётся. LocalOS владеет доступом, записью очереди и результатом отправки.

POST `/api/business/<business_id>/client-handoffs/<conversation_id>/notify-self-test` не принимает recipient_user_id/chat_id. Запрос не включает агента, не принимает диалог автоматически и не создаёт бронь. Кнопка «Уведомить меня в Telegram (тест)» видна только у ожидающего синтетического обращения.

## Ссылка и результат

Кнопка Telegram «Открыть диалог LocalOS» содержит HTTPS URL с section=clients, view=handoffs, business_id, scope_type=business и conversation_id. Авторизация LocalOS остаётся обязательной. Inbox выбирает обращение только после проверки его наличия в списке текущего бизнеса; чужая/недоступная ссылка показывает ошибку без загрузки переписки.

Результат сохраняется как aiagentmessages.message_type=handoff_notification. Row lock диалога сериализует создание claim; sending сохраняется до внешней отправки. sent/unknown/sending для того же пользователя блокируют повтор. Только failed после явного повторного нажатия допускает новый вызов. При падении после claim повтор запрещён до ручной сверки; автоматический retry не добавлен.

`sent` означает, что Telegram Bot API подтвердил отправку и вернул message_id. Это **не подтверждение получения push, доставки на устройство или прочтения**. Статусы sending/unknown не выдаются за успех; UI не показывает технический JSON. Принятие отдельно фиксируется обычным handoff_accept с actor, затем возможны внутренний ответ и завершение на паузе.

- Изменений схемы базы нет. Используются существующие сообщения аудита.

Для проверки выбран аккаунт, который принимал предыдущий внутренний диалог в браузере; имя и email сверены с аккаунтом пользователя, Telegram привязан. Рассылка Иринам/другим сотрудникам не настраивалась.

- Во встроенном браузере создано обращение `f4fe0056-2277-48db-8e2b-d19b319654d5` для Расчёски на Долгоозёрной.
- Нажата только кнопка отправки себе. Telegram подтвердил отправку, message_id **1437**; receipt actor и recipient_user_id совпали с аккаунтом пользователя. Реальным сотрудникам ничего не отправлялось. Пользовательское подтверждение получения на устройстве/прочтения пока отсутствует.

Состояние human_active, is_agent_paused=1; handoff_accept содержит того же actor. Это проверка действия в браузере, а не заявление, что пользователь лично принял обращение в Telegram.

- PostgreSQL: одна запись handoff_notification со статусом sent и одна handoff_accept, оба enabled=false. Тест оставлен в human_active на паузе для осмотра пользователем. Внешний клиентский канал и CRM не включались.
- Каноническая запись теста/доставки находится в aiagentmessages этого обращения. Это внутренний self-test, не продажная коммуникация: deal, задача YouGile и follow-up не создавались.
