# LocalOS: подготовленный пакет 6 сентября

Статус: **локальная подготовка; production не выпущен**. Это первый пакет исполнения [плана R0–R7](LOCALOS_IMPLEMENTATION_PLAN_2026-09-06.md), а не завершение всего плана. Фактические проверки и остаток — в [отчёте реализации](LOCALOS_IMPLEMENTATION_STATUS_2026-09-06.md).

## Состав и граница выпуска

- Исправления доступа, поздних ответов, предпочтений и повторов запросов; выбранное направление на «Сегодня» даёт полезный следующий шаг даже без текущих задач.
- Compiled-проверка таблицы: собственные примеры → проверка → утверждение конкретной версии → повторные исполнения → отчёт. Новое исполнение отделено от сетевого повтора. Runtime не вызывает модель; генерация модели требует отдельного настоящего пилота.
- Атомарный admission, lease/fencing, отдельные короткие транзакции compiled runner, защищённый указатель утверждённой версии, ограничение компиляций, snapshots и удаление рабочих таблиц по сроку хранения.
- Двенадцать Alembic-ревизий, часть runtime DDL перенесена в миграции, подготовлен отдельный migrator и режим запуска с проверкой схемы. Полный TypeScript check проходит без baseline-исключений.

В production-пакете compiled UI/preview/execute, сбор активности и предложения смены приоритета выключены. `VITE_BROWSER_COOKIE_AUTH_ENABLED=false` сохраняет действующий bearer-вход: переменная cookie-режима не задана ни в окружении production app, ни в загружаемом им `.env`, а backend default — false. Cookie-авторизация отдельно проверена в isolated staging; её включение не входит в этот выпуск. Ручной приоритет «Сегодня» включён. Сохраняется текущий worker `all`; `docker-compose.workers.yml` и runner fragment не включаются этим выпуском. Права runtime БД не сокращаются глобально: дополнительные DDL callers и legacy provider transactions остаются в следующем пакете.

Не включать `COMPILED_SCRIPT_ADVANCED_ENABLED` для обычных пользователей. Ручной исходник использован только в изолированной synthetic staging-проверке; это не свидетельство успешной генерации моделью.

## Подготовка после разрешения выпуска

Все серверные командные блоки начинать с `cd /opt/seo-app`, длительные операции выполнять в именованной tmux-сессии. Не выгружать секреты `.env` в логи или в локальный пакет.

1. Повторить `docker compose ps`, свежие app logs, `curl -I http://localhost:8000`, затем read-only проверки head, flags и очередей. Прежний preflight зафиксировал head `20260905_004` и ноль queued/running agent runs; это наблюдение, а не гарантия состояния во время выпуска.
2. Сверить live hashes затронутых файлов внутри app, worker и Telegram-контейнера. Уже проверенные 48 путей app совпали с исходным `ffc54c19` либо отсутствуют как новые; доказательство — `raw/production-live-source-hashes.json`. При новом расхождении ничего не перезаписывать до разбора.
3. Создать защищённый каталог `/opt/seo-app/releases/<release-id>/backup/`, сохранить действующие source/dist, миграции, entrypoint/scripts, Compose и конфигурацию на сервере. Снять свежий custom-format PostgreSQL dump, проверить `pg_restore --list`, полное чтение dump без восстановления и SHA-256. Старый backup 5 сентября не заменяет свежий.
4. Перед заменой исполняемого кода дождаться завершения затронутой работы, при необходимости временно остановить её новое admission. Не запускать одновременно старого и нового владельца очереди. Не считать нулевое число agent runs доказательством пустоты parser/Telegram/прочих очередей.
5. Из согласованного manifest копировать только файлы пакета в `/opt/seo-app/src`, соответствующие migration/script пути и затронутые контейнеры. Новые frontend assets добавлять с сохранением assets прежней сборки для открытых вкладок. Не заменять серверные Compose и `.env` целиком локальными файлами: в них есть независимые настройки. Добавить только согласованные переменные и bind mounts двух startup-скриптов этого выпуска. Файлы `scripts/localos_migrator.py` и `scripts/check_content_learning_schema.py` должны существовать на хосте до recreate; копирование только внутрь прежнего контейнера потеряется при его пересоздании.
6. Одним migrator выполнить `python scripts/localos_migrator.py upgrade`, затем `python scripts/localos_migrator.py check`. Advisory lock сериализует этот путь. Мигратор должен получить действующее окружение приложения; не передавать пароль аргументом командной строки.
7. Для app/worker выставить `LOCALOS_MIGRATION_MODE=schema-check-only` после успешной миграции. Сохранить нынешние DB-права. Lean Telegram-контейнер запускается напрямую без app entrypoint; перезапускать его после успешного schema check, не назначать ему несуществующий migrator. Изменение container environment требует recreate только затронутого сервиса; один `restart` новые переменные не применяет. Если среда уже соответствует, достаточно частичного source update и restart app/worker/Telegram.
8. Проверить hashes живых файлов в каждом затронутом контейнере, head, Compose status → app logs → HTTP health → целевые endpoints. Проверить Today, доступ чужого scope, scoped preferences, существующий blueprint/историю и browser desktop/mobile на разрешённых данных. Для state-changing smoke использовать только отдельный согласованный тестовый tenant, не данные клиента.

Git commit, push, архив payload и их SHA-256 фиксируются отдельно в evidence. Отсутствие авторизации GitVerse пока препятствует push; наличие локального коммита не означает remote backup или deployment.

## Откат

Сначала выключить новое admission/пилот, если он был отдельно включён, и проверить активные попытки. Вернуть прежние source/frontend из свежего server backup; **сохранить новые entrypoint, standalone migrator, schema checker и полную migration directory**. Запускать с `schema-check-only` на расширенной схеме. Не делать downgrade и не восстанавливать старую БД поверх новых данных автоматически.

Этот вариант проверен в отдельном контейнере: backend `ffc54c19`, новая схема `20260906_012`, новые startup scripts; health, вход и Today вернули 200 (`raw/staging-rollback.txt`, EXIT=0). Проверка подтверждает совместимость этого сочетания, но не подменяет проверку фактического server backup и всех production-сценариев.

Если причина отката — миграция или повреждение данных, восстановление БД требует отдельного решения с учётом новых записей и времени простоя. Автоматическое восстановление широких DDL-прав не входит в процедуру.
