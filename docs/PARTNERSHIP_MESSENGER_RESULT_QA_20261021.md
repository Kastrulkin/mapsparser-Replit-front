# Messenger partnership letters: visible preparation and correct results

The mobile partner card previously treated an accepted background request like a completed action, displayed feedback behind the card, and kept the user away from the existing letter. The bot then treated any result containing drafts like a batch of map-review replies. A live Telegram pass reproduced both failures without sending a letter to a partner.

The card now opens an existing letter without queuing generation. The letter list is limited to the selected partner until All letters is chosen. For a new preparation, status and errors appear inside the card; Check readiness reads the existing job and refreshes saved letters. It does not start another generation. Limit, missing-contact, missing-evidence, stopped and unknown states do not pretend that a letter is ready. Network/server errors retain local edits and show an actionable message without internal diagnostics. Scope changes and access revocation retain the already deployed data-clearing boundaries.

The shared bot formatter applies map-review instructions only to the explicit bulk-review intent. Reading a selected partner shows the latest saved letter, its actual recipient and contact source, with a service/legal-email warning when applicable. Older generated variants are not appended. Viewing a letter does not approve or send it.

A deliberate Telegram bot handoff opens the authorized link and closes the miniapp so that the bot response is visible. A failed handoff leaves the miniapp open. MAX uses its existing bridge and shows instructions if the chat remains covered; no undocumented MAX close method is assumed. Current platform contracts: [Telegram Mini Apps](https://core.telegram.org/bots/webapps), [MAX Bridge](https://dev.max.ru/docs/webapps/bridge).

The common source also preserves the deployed mobile dialog, unsaved-card guard, scoped launch filters, recipient-source review, access-revocation behavior and search empty-state fixes. Existing result links keep business and partner filters; services/reviews open their own section rather than the map parser.

Validation: the incorrect generic bot formatting failed its focused regression before the fix. Final checks passed: 19 frontend cases on the production-based source, 24 adjacent frontend cases on the common source, 48 backend cases, and both frontend builds. Live Telegram confirmed the selected existing letter opens from its card and the bot returns one latest letter without duplicated map-review instructions. Isolated browser checks covered draft save, network failure, server failure, version conflict, explicit retry and revoked access. These counts are technical checks, not completion of the 170-case client acceptance matrix. Fresh AI generation, live MAX and physical-device checks remain separate requirements. No client or partner messages were sent.

A delayed-save browser pass additionally reproduced silent loss of text typed while an earlier version was saving. The shared mobile letter field, approval and deletion are now disabled for the in-flight operation; Save shows a visible saving state. The focused regression failed before the change and passed afterwards (17 production-source and 18 common-source cases, including adjacent preparation cases). Both frontend builds passed. The protected state was checked in the isolated browser, and the production-based frontend was partially deployed with source/index guards and a live HTTP 200 check. This does not certify simultaneous unsaved edits in several separate letters.
