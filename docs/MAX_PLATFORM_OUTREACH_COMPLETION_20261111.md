# MAX: входящие и новый поиск для всей платформы

Дополнение к исправлению `de3c432`. Выбор LocalOS открывает платформенный аутрич без обязательного выбора клиента. Проверено локально; production не обновлён.

## Что работает в коде

- В «Партнёрствах» для LocalOS отображаются человеческие ответы по всем бизнесам, включая ответы workstream без campaign. Список содержит 20 ответов на страницу с подгрузкой по устойчивому курсору; в чате остаётся компактная сводка.
- «Проверить входящие» и команда «Проверь входящие по всем бизнесам» создают долговечное задание существующей очереди. Оно использует готовые сборщики email, Telegram и VK. Личные диалоги MAX не читаются; сообщения не отправляются. Один проход ограничен лимитами адаптеров, частичные ошибки и отсутствие доступных источников показаны явно.
- Повторные запросы одного пользователя используют уже активную проверку. Текущее право superadmin и активность системного бизнеса проверяются при запросе и перед каждым каналом в воркере. Итог проверки сохраняется в существующей истории чата с проверкой действующей lease задания.
- «Новый поиск» позволяет указать аудиторию, географию, число компаний и источник. Поиск готовит проверенные контакты в режиме `find_only`; письма не готовятся и не отправляются. Сначала показаны условия и расходы. Запуск использует существующее подтверждение Operator и повторную проверку прав, версии условий и баланса.
- Системный бизнес LocalOS не требует второй записи в `OUTREACH_CONTINUATION_BUSINESS_IDS`. Общий выключатель поиска сохраняется. Право записи обычного участника системного бизнеса не заменяет текущее право superadmin.
- В разделе показаны последние 50 поисков разных бизнесов и их сохранённые стадии. Кнопка обновления получает актуальное состояние. Ошибка доступа удаляет приватные данные из интерфейса; временная ошибка сети позволяет повторить загрузку.

## Общая конфигурация

Compose передаёт приложению, воркеру и owner-боту одинаковые `LOCALOS_PLATFORM_BUSINESS_ID`, `OUTREACH_REPLY_SYNC_ENABLED`, `OUTREACH_CONTINUATION_ENABLED` и правила обычных бизнесов. Все три сервиса читают существующий необязательный `config/outreach-search.env`; секреты в репозиторий не добавляются. MAX использует общие обработчики в приложении, Telegram — отдельный owner-бот.

Для реального запуска должны существовать активный системный бизнес и действующий superadmin. `OUTREACH_CONTINUATION_ENABLED=true` включает поиск; прежний default `false` сохранён. Нужен настроенный поисковый сервис. Платный Яндекс выбирается явно и показывается в условиях до подтверждения. Неисправный/отключённый поиск не подменяется картами. `OUTREACH_REPLY_SYNC_ENABLED=false` останавливает новые проверки входящих.

## Реализация

- `src/api/operator_platform_outreach_api.py`: защищённые просмотр, очередь обновления и подготовка условий поиска через существующую транзакцию чата.
- `src/services/operator_platform_outreach.py`: страницы входящих, поиски, готовность, постановка проверки и переиспользование сборщиков ответов.
- `src/services/operator_platform_context.py`, `operator_async_jobs.py`: явная проверка входящих из чата и обработка задания.
- `src/services/outreach_continuation.py`: доступ системного контекста при сохранении общих выключателей и проверки текущего администратора.
- `frontend/src/components/telegram/PlatformOutreach.tsx`: платформенный раздел для MAX/Telegram с существующей авторизацией miniapp и существующим endpoint подтверждения Operator.

## Проверки и выпуск

79 pytest и 39 Vitest прошли. В том числе: реальные API-функции и транзакция чата, сохранение approval без создания поиска до подтверждения, обработка задания существующим воркером, отозванные права, demo/impersonation, изоляция обычных бизнесов, пагинация, частичная ошибка канала, запуск через существующий action endpoint. Внешние провайдеры в тестах заменены; реальных поисков, списаний и production-записей не выполнялось.

Frontend production build прошёл. Общая проверка TypeScript содержит те же 57 диагностик исходной MAX-ветки; новых диагностик нет. Тесты без PostgreSQL не заменяют проверку запросов на живой схеме и приёмку в MAX на устройстве.

Миграции не требуются. Перед выпуском сверить настройки без вывода секретов, сделать частичное обновление исходников и dist. Изменение Compose environment/env_file требует пересоздания затронутых контейнеров, простого restart недостаточно. Затем проверить Compose status, логи приложения, локальный HTTP и авторизованные сценарии: LocalOS → Партнёрства → все ответы → проверка входящих → условия нового поиска → подтверждение. Реальный платный поиск при проверке требует отдельного подтверждения показанных условий.
