# Защита текстового Оператора: включение 13.11.2026

Статус: **`beta`, защита включена**. Эффективная конфигурация: `enabled=true`,
`scope=operator_text`, `mode=enforce`. Настройки действуют в приложении и
Telegram-обработчике. При приёмке 13.11 связь бота с Telegram API нарушалась.
**Повторная проверка 16.11.2026 подтвердила восстановление связи**: контейнер healthy,
`getMe` — HTTP 200 / ok, свежий polling heartbeat. Прежний блокер закрыт.

## Охват и границы

Защита применяется к общему `operator_chat_service.process_chat`: текстовый
Оператор веб-приложения и owner-бота Telegram. Приложение, worker,
operator-worker, outreach-worker и telegram-bot используют один TLS-распознаватель
piighost/Presidio и отдельный Redis с шифрованными соответствиями.

Исходящий текст подменяется перед моделью; ответ восстанавливается для пользователя.
Публичные названия и адреса разрешаются только по авторизованным сохранённым
снимкам карточек, в точных диапазонах окончательного prompt. Частное совпадение
с публичным названием само по себе исключения не получает.

Область запроса назначает серверный обработчик, независимо от присланного
`channel`. Она сохраняется в существующем shadow-контексте и очищается при
завершении/исключении. Если защиту включили во время обработки запроса,
последующие попытки LLM уже проходят через неё. Неподключённый прямой LLM-вызов
в защищённом контексте отклоняется. Правила восстановления ограничены проверенными
строковыми полями семи контрактов; scope, права, URL и маршрутизация не
восстанавливаются. Внешние действия сохраняют ручное подтверждение.

Голос/транскрибация, файлы, мультимодальные вызовы, остальные AI-функции и фоновые
задачи вне этого общего обработчика не охвачены этим включением. Это обратимая
псевдонимизация; она не гарантирует обнаружения любых персональных данных и не
является подтверждением юридического соответствия.

## Конфигурация

- `/etc/localos/pii/activation.json`: root, `0600`, только `version=1`,
  `enabled=true`, `scope=operator_text`, `mode=enforce`.
- `/etc/localos/pii/client.json`: прежний API-конфиг из четырёх полей; ключ
  шифрования и Redis credentials в приложение не передаются.
- Текущие контейнеры получают защищённые копии настроек и API-конфига. Уже
  существующий read-only mount outreach-worker сохранён. Для контейнеров без
  явного `PII_RUNTIME_TRANSPORT=shared` штатный `auto` выбирает общий runtime
  по существующему API-файлу; тип клиента проверен из всех пяти процессов.
- Явное значение файла активации перекрывает старое выключенное/отсутствующее
  environment. Вне доверенного запроса Оператора `enabled()` остаётся false.
- Канонический Compose-профиль автоматически подключён через `COMPOSE_FILE`
  в серверном `.env`; он задаёт `shared`, область `operator_text`, обязательность
  активации и два read-only bind с `create_host_path:false` для будущих контейнеров.
- Серверный файл `src/services/pii_protection/.activation-required` содержит
  только маркер обязательной конфигурации, без секретов. Он находится в общем
  read-only source mount и переживает пересоздание контейнера. Если privacy-профиль
  случайно пропущен и конфигурация отсутствует, запрос блокируется до модели.
  Не удалять этот файл при синхронизации исходников. В локальном checkout маркер
  не включён по умолчанию.

При прежних пересозданиях четыре контейнера потеряли явный shared environment
и read-only client mount. Частная сеть сохранилась. При этой выкладке API-файлы
восстановлены, конфигурация для будущего пересоздания сверена, а случай пропуска
профиля дополнительно закрыт серверным маркером. Образы и остальные настройки
текущих контейнеров сохранены; полного пересоздания рабочих контейнеров не было.

В runtime изменён только `synthetic_only: true → false`, чтобы принимать обычные
идентификаторы авторизованных рабочих запросов. Fernet/Bearer, CA, Redis URL/ACL,
TTL **900 секунд** и квоты **10 protect/с общая**, **4/с на бизнес**, burst 4
сохранены. Счётчики квот находятся в одном процессе и сбрасываются при рестарте;
для нескольких реплик потребуется отдельное решение. Автоматического перехода
на открытый текст при ошибке/квоте нет.

бот запускается напрямую. Обычный авторизованный трафик после включения является
рабочей эксплуатацией, а не частью ручного теста.

## Отказ, восстановление и обслуживание

При инциденте использовать `enabled=true, scope=operator_text, mode=blocked`,
обновив host-файл и копии в текущих пяти контейнерах. Host-файл менять с сохранением
inode, поскольку будущие read-only single-file bind mounts привязаны к нему.
Сохранять `root:root`, `0600`. Для контейнеров с правильным read-only bind достаточно
host-файла; для остальных копия обновляется через временный файл и rename.
`blocked` проверен: вызовов провайдера — 0.

`enabled=false` возвращает прежние маршруты и не является безопасным аварийным
откатом. Откат исходников выполнять только после остановки чувствительных запросов.
Сначала восстановить runtime/Redis/конфигурацию, пройти синтетический canary и лишь
затем вернуть `mode=enforce`. Не удалять marker, ключи или изолированный Redis.

Все VPS-выкладки должны сохранять канонический Compose-профиль; собственный `-f`
должен явно включать `docker/pii-runtime/compose.client.fragment.yml`. Публикации,
отправки и другие действия от имени бизнеса по-прежнему требуют подтверждения.

## Итог и доказательства

Защита включена 13.11.2026; рабочий `mode=enforce` восстановлен после контрольной
блокировки. Последняя сверка: **2026-11-13T12:46:21Z**. HTTP `/`, `/health`,
`/ready` и `https://localos.pro` — 200. Оба PII-контейнера healthy; все пять клиентов
используют один процесс модели. Проверены пять отдельных созданных контейнеров
с privacy-настройками и случай ошибочного пропуска профиля. Временные PostgreSQL
и обе собственные тестовые сети удалены. Образы/материалы приёмки сохранены.

Выкладка встретила два события: 90-секундное ожидание рестарта outreach-worker
не уложилось в его 900-секундный период завершения; параллельная серверная
выкладка затем пересоздала обработчик. Текущий контейнер перепроверен, его
остальные настройки и образ сохранены. Служебная ошибка финализатора активировала
аварийный `blocked` mode; ошибка исправлена, проверки повторены, `enforce` возвращён.
Продуктового отката на открытый текст не было.

Финальная проверка границ дополнительно уточнила, что серверный marker требует
конфигурацию именно при входе в доверенный запрос Оператора. Вспомогательные
процессы вне этой области без privacy-профиля сохраняют прежнее выключенное
поведение. После правки повторены 74 модульные, 12 полных сценариев и 1 проверка
настоящей HTTP-квоты — всего 87 без ошибок/пропусков. Повторный тест лимитера
допускает уже включённый runtime, продолжая использовать исключительно
синтетические scope и отдельную тестовую БД.

Резервные копии: `/opt/seo-app/backups/pii-enable-20261113T120831Z` (исходники),
`/etc/localos/pii/backups/enable-20261113T120831Z/runtime.json.before` (защищённая конфигурация runtime).
API-only client.json не менялся; ключи и квоты повторно сверены. Значения секретов
в отчёт не включены. Проверка журналов возвращала только счётчики, без содержимого.

Проблема на момент 13.11 — **живой канал Telegram** (проверка 16.11 ниже). Контейнер бота работает, но его
healthcheck не проходит: нет свежего polling heartbeat, `getMe` через текущий HTTP-
прокси завершается таймаутом. TCP к прокси доступен из host и namespace бота;
маршрут контейнера корректен. Запрос к Telegram через этот прокси зависает также
с host. Публичный и private SSH на OpenClaw не дошли до авторизации, поэтому
восстановить канал сервера не удалось. Это `REPRODUCED`, исправление не доказано.
Проверка не отправляла сообщений и не вызывала `getUpdates` вторым получателем.
Синтетические веб/бот-сценарии проходят; полноценная онлайн-приёмка Telegram
