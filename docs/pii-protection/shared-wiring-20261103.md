## Применение и восстановление

Установлены только `gateway.py`, `remote.py`, `runtime_config.py`,
`runtime_logging.py`, `runtime_server.py`. Каждый клиент подключён к существующей
закрытой сети и получил файл конфигурации `0600` с адресом, API-токеном и публичным
CA. Fernet-ключ и доступ к Redis остались только у runtime.

Перезапуски выполнялись последовательно: `operator-worker`, `outreach-worker`,
`worker`, `telegram-bot`, затем `app`. Контейнеры не пересоздавались:
их ID сохранились. Для приложения и обработчиков оставлен режим
`schema-check-only`; у бота отсутствует миграционный entrypoint.

Первый проход автоматически откатился: проверка доступности обратилась к app
до завершения его запуска. После отката отдельно подтверждены исходные хэши,
сети, отсутствие активного клиентского файла и HTTP 200. Повторный проход с
ограниченным ожиданием HTTP-готовности завершился успешно. При независимой
проверке заменён несовместимый `docker top` на чтение имён процессов через `/proc`;
дополнительных перезапусков для этого не потребовалось.

Резервные копии на VPS: `/opt/seo-app/backups/pii-shared-20261103T112543Z`
и `/opt/seo-app/backups/pii-shared-20261103T113554Z`. Исходные файлы и неактивные
клиентские конфигурации первого прохода сохранены. Изменений посторонних файлов
откат не выполнял. При итоговой проверке у outreach-worker замечен более поздний
StartedAt, чем у завершённого нами прохода; причина этого отдельного перезапуска
не устанавливалась. Его ID, подключение, выключенный флаг и проверки сохранены.

[Отчёт и десять тестовых созданий](shared-persistence-20261103.md).

[compose.client.fragment.yml](../../docker/pii-runtime/compose.client.fragment.yml).

Живые контейнеры в этапе закрепления не пересоздавались: ранее скопированные файлы
`0600` продолжают работать до следующего пересоздания.

проверяются допустимые задачи, публичный контекст, разрешённые поля восстановления
и интенсивность запросов; synthetic-only gate пока ограничивает диагностический
контур.
