# Постоянное подключение общего PII-процесса — 03.11.2026

Статус: `internal`, `persistent_flag_off`. Подключение app, worker,
operator-worker, outreach-worker и telegram-bot закреплено в автоматической
конфигурации VPS. Рабочие контейнеры в этом проходе не перезапускались и
не пересоздавались. Флаг выключен, `synthetic_only=true` сохранён.

## Что закреплено

В `/opt/seo-app/.env` изменена только строка выбора Compose-файлов:

```dotenv
COMPOSE_FILE=docker-compose.yml:docker/compiled-script-runner/compose.fragment.yml:docker/pii-runtime/compose.client.fragment.yml
```

Обычные команды `docker compose` из `/opt/seo-app` теперь автоматически включают
[PII-профиль](../../docker/pii-runtime/compose.client.fragment.yml). При следующем
пересоздании пяти сервисов он задаёт:

- `PII_PROTECTION_ENABLED: "false"`, `PII_RUNTIME_TRANSPORT: shared` и фиксированный путь клиентского файла;
- read-only bind `/etc/localos/pii/client.json` → `/run/secrets/localos-pii-client.json`;
- `create_host_path: false`: отсутствие секрета блокирует создание контейнера;
- существующую обычную сеть и дополнительную внешнюю сеть `localos-pii-private`.

Сети compiled runner, прежние mounts, команды, образы, зависимости, migration mode
и все остальные параметры сохранены. Это проверено сравнением полной эффективной
конфигурации до и после; пустые сетевые настройки `null` и `{}` нормализованы как
эквивалентные. Прочие байты `.env` сохранены. Основной `docker-compose.yml` и
профиль compiled runner не менялись; локальный общий Compose не заменял серверный.

API-токен остаётся в существующем клиентском файле `0600`; значение не внесено
в Compose, `.env`, Git или отчёт. Ключ шифрования и Redis credentials клиентам
не передавались. Текущие рабочие контейнеры продолжают использовать ранее
скопированный файл; read-only mount применяется при их следующем пересоздании.

## Проверки

Созданы десять отдельных синтетических контейнеров: по два последовательных
создания для каждого сервиса. Использованы те же неизменяемые image ID, что у
живых сервисов, и PII-настройки из закреплённой конфигурации. Каждый цикл получил
новый ID. Рабочие entrypoint, mounts с бизнес-данными, окружение с доступом к БД,
порты и запуск зависимостей в диагностические контейнеры не переносились.

Все десять проверок прошли: флаг `false`, API-only клиент, файл `0600` на
read-only mount, доверенный TLS, `synthetic_only=true`, синтетическая подмена
и точное восстановление строки. Общий PID модели — 12453; обычный исходящий
маршрут сохранён. После проверки тестовые контейнеры удалены.

Отдельно подтверждены отказ создания при отсутствующем клиентском файле и
отсутствие автоматически созданного каталога на его месте. Попытка передать
`PII_PROTECTION_ENABLED=true` и другой транспорт через родительское окружение Compose не меняет
явные значения профиля. Сам клиентский секрет остался побайтово прежним.

Из всех пяти живых контейнеров дополнительно проверены выключенный флаг,
прежний путь при выключенной защите и доступ к одному shared runtime. ID и
StartedAt рабочих контейнеров сохранились. Все основные сервисы работают,
PII runtime/Redis и Telegram-бот имеют `healthy`. Главная, `/health`, `/ready`
и публичный адрес отвечают HTTP 200 до и после тестов; в проверенном фрагменте
логов приложения ошибок нет.

Диагностика использовала только вымышленные строки и `synthetic-*` scope;
бизнес-записи не читались и не менялись, миграции, внешние LLM-вызовы и отправки
сообщений не выполнялись. Прежние проверки корпуса, нагрузки и отказов:
[общий runtime](shared-runtime-20261103.md).

## Эксплуатация и откат

Для стандартного запуска дополнительный `-f` больше не требуется. Если будущая
операция явно переопределяет `COMPOSE_FILE` или передаёт собственный список `-f`,
в нём также должен оставаться PII-профиль. Новый профиль не включает защиту
рабочего трафика; изменение флага и synthetic-only gate не входит в эту выкладку.

Резервная копия на VPS: `/opt/seo-app/backups/pii-config-20261103T122201Z`.
Каталог `0700`, исходный `.env` и прежний PII-фрагмент сохранены с правами `0600`.
Откат конфигурации — вернуть эти два файла после проверки отсутствия чужих
изменений; контейнеры автоматически при этом не перезапускаются. Для отката
после будущего пересоздания потребуется отдельно сохранить рабочие сети и
клиентский файл, как при [первом подключении](shared-wiring-20261103.md).
