# Web tracking: production contract and rollout

Status: `beta`, disabled by default. This document is the operational and privacy contract for the LocalOS website tracker.

## Scope and safety boundary

The tracker observes anonymous navigation and target-action signals. It does not change the client website and does not implement chat, personalization, session replay, heatmaps, fingerprinting, keystroke recording, or AI analysis of individual sessions.

### Stored allowlist

| Category | Stored | Never stored |
| --- | --- | --- |
| Visitor | Random `v_…` identifier | Fingerprint, account identity, analytics IP |
| Session | Random `s_…` identifier, timestamps, landing path | Authentication state, cookies from the client site |
| Page | Allowlisted hostname, pathname, bounded title | Query string, page HTML, private element contents |
| Referrer | Scheme and hostname only | Referrer path and query string |
| UTM | `source`, `medium`, `campaign`, `term`, `content` with length limits | Arbitrary query parameters |
| Click | Tag, bounded visible label, safe href origin/path | DOM snapshot, coordinates of every click, form values |
| Form | Start/submit fact, bounded form ID/name/action | Values of input, textarea, select, phone, email, comments, passwords |

Control characters are removed and text is normalized to Unicode NFC before storage. External URLs are reduced to their origin. `tel:` and `mailto:` values are reduced to the scheme, so phone numbers and email addresses are not stored.

## Consent integration

Load in denied mode when the client site requires prior consent:

```html
<script async src="https://localos.pro/tracker.js"
  data-business="PUBLIC_TRACKER_ID"
  data-consent="denied"></script>
```

Then connect the client consent manager:

```js
window.LocalOSTracker.setConsent(true);  // start anonymous collection
window.LocalOSTracker.setConsent(false); // stop collection and clear queued events
```

Denied mode does not create LocalOS visitor or session identifiers in browser storage. LocalOS provides the mechanism; the website owner remains responsible for deciding when consent is required and for the wording of its privacy notice.

## Idempotency and compatibility

- Current tracker version: `1.2.2`.
- Current event schema: `2`.
- Schema `1` remains accepted during the transition; the server derives a deterministic event ID.
- Schema `2` requires a random `event_id` generated by the tracker.
- `(tracker_id, event_id)` is unique. Replayed batches return separate `accepted` and `duplicates` counts.
- The browser retries a failed 5xx batch once. Its in-memory queue is capped at 100 events.

## Domain boundary

Each tracker has an exact hostname allowlist. The public payload cannot select a business. Ingestion resolves the tenant only from `public_tracker_id` and rejects events from hostnames not configured by an authorized LocalOS user. Add apex and `www` hostnames separately where both are used.

## Analytics semantics

Session attribution is fixed from the first event of the session. A non-empty UTM source has priority; otherwise the canonical source type is `search`, `social`, `maps`, `referral`, `direct`, or `unknown`. This is a simple first-session-source model, not a multi-touch marketing attribution system.

Observed target events are stored separately from their canonical classification. Supported action types are `form`, `phone`, `email`, `whatsapp`, `telegram`, `booking`, and `outbound`, with a safe provider/domain where available. A `booking` event means that the visitor followed a booking link; it does not prove that an appointment was completed.

Engagement uses a 30-second heartbeat only while the tab is visible plus a bounded `page_leave` checkpoint. Each interval is capped at 30 seconds, is queued with other events, and never counts background-tab time. It does not record mouse movement, keystrokes, DOM state, or a session replay.

## Feature flags and rollback

All backend flags default to `false`:

| Variable | Purpose |
| --- | --- |
| `WEB_TRACKING_ENABLED` | Master backend switch |
| `WEB_TRACKING_CREATE_ENABLED` | Permit creation of new trackers |
| `WEB_TRACKING_INGEST_ENABLED` | Accept public event batches |
| `WEB_TRACKING_ANALYTICS_ENABLED` | Serve analytics reads |
| `WEB_TRACKING_BUSINESS_IDS` | Optional comma-separated pilot allowlist; `/auth/me` uses it to expose the dashboard capability only for eligible businesses |
| `WEB_TRACKING_IN_PROCESS_RATE_LIMIT` | Per-process defense-in-depth batch limit; keep aligned with the intended IP+tracker limit and raise only for approved load tests |
| `WEB_TRACKING_METRICS_REDIS_URL` | Shared 48-hour ingestion counters and latency histogram; defaults to the Docker Redis instance |
| `VITE_WEB_TRACKING_ENABLED` | Include the dashboard navigation and route in a frontend build |

Safe rollback order: hide UI → stop tracker creation → stop ingestion → keep analytics reads available. Do not downgrade or drop tracking tables during an ordinary application rollback.

## Limits

- 25 events per batch;
- 64 KiB request body;
- 4 KiB sanitized metadata per event;
- 1,000 raw events per session;
- 20 allowed domains per tracker;
- 120 batches/minute per IP+tracker;
- 12,000 batches/minute global emergency limit.

Flask-Limiter uses Redis in Docker (`RATE_LIMIT_STORAGE_URI=redis://redis:6379/0`). Public tracker IDs are not secrets and are never the only abuse-control boundary.
The in-process limiter defaults to the same 120 batches/minute. It is intentionally configurable so an approved stage load test can raise both limits together; production should retain the conservative default until capacity evidence supports a change.

The application runs under Gunicorn with conservative bounded concurrency (`WEB_CONCURRENCY=2`, `WEB_THREADS=4` by default), limiting simultaneous per-request PostgreSQL connections. These values are capacity settings, not universal recommendations; tune them only from the stage load profile and the production PostgreSQL connection budget.

## Retention

Default raw-event retention is 180 days and may be configured per tracker between 90 and 365 days, so the longest 90-day interface period remains exact. Daily aggregates default to 730 days and may be configured between 365 and 1,825 days. Every aggregate run reconciles the total event count against raw events before retention can delete that day. Business deletion cascades through trackers, sessions, visitors, events, and aggregates.

The existing worker runs aggregation and bounded cleanup only when `WEB_TRACKING_MAINTENANCE_ENABLED=true`. It defaults to dry-run; destructive cleanup additionally requires `WEB_TRACKING_MAINTENANCE_DRY_RUN=false` after review and approval. Raw ingestion remains limited to the pilot allowlist until the retention job has completed successfully in dry-run and active modes.

The superadmin deletion flow is deliberately two-step:

1. `POST /api/admin/business/<business_id>/web-tracking/delete` with `{"dry_run": true}` records a reviewed count snapshot.
2. Disable collection for every tracker of the business and review that the counts have stopped changing.
3. Within 24 hours, repeat with `dry_run: false`, the exact `confirm_business_id`, and `acknowledge_irreversible: true`.

Both API calls create durable audit rows. The execute step is rejected if collection is active, if counts differ from the reviewed snapshot, or if the same superadmin has no dry run from the previous 24 hours. Production use still requires the operational backup and approval policy.

## Logs and observability

The ingestion route emits one structured log record per request with outcome, HTTP status, latency, request size, accepted count, duplicate count, and a non-reversible short hash of the public tracker ID. It never logs request bodies, event metadata, visitor IDs, session IDs, hostname, IP, or business ID.

Every ingestion response also updates a shared Redis minute bucket with request/event counts, accepted/duplicate/rejected totals, HTTP classes, safe outcomes, and an exclusive latency histogram. Buckets expire after 48 hours. Redis failure is swallowed and rate-limited in logs, so telemetry can never turn an otherwise valid ingestion request into an error.

`GET /api/admin/web-tracking/health` is superadmin-only and returns aggregate tracker activity, event rates, schema versions, PostgreSQL table/index sizes, safe per-tracker status, error codes, recent maintenance checks, and shared 60-minute p50/p95/p99 ingestion telemetry without event contents. The admin **Sites** tab renders the same privacy-bounded support view and blocks rollout visually when 5xx is non-zero or p95 exceeds 1,000 ms.

Durable latency dashboards and alert delivery are still derived from the structured ingestion logs in the production log/metrics backend. A release is not ready for pilot until alert delivery has been exercised; the 48-hour in-app diagnostic view is a rapid support signal, not a replacement for durable monitoring.

Verify the real Redis contract after a deployment or Redis configuration change:

```bash
cd /opt/seo-app
docker compose exec -T app python scripts/check_web_tracking_redis.py
```

The check uses a random `localos:web_tracking:qa:*` namespace, validates counters, TTL and latency percentiles, and deletes its exact temporary key in `finally`. It does not read, overwrite, or delete live ingestion buckets.

Initial alerts:

- 5xx rate above 1% for 5 minutes;
- p95 ingestion latency above 750 ms for 10 minutes;
- rejected-event rate changes by more than 3× baseline;
- no accepted events from all pilot trackers for 30 minutes during expected traffic;
- `web_events` storage grows more than 25% day-over-day;
- unsupported schema version appears;
- `/tracker.js` is not HTTP 200 JavaScript.

Technical proxy/application logs should be retained for no more than 14 days unless an incident requires a documented extension. Access is limited to infrastructure operators. Nginx access logging is disabled specifically for `/api/tracking/events`.

## Deployment gate

Before any production schema change, create a PostgreSQL backup. Run every server command from `/opt/seo-app`.

```bash
cd /opt/seo-app
docker compose ps
docker compose logs --since 15m app
curl -I http://localhost:8000
curl -I https://localos.pro/tracker.js
```

Required evidence before enabling the first pilot business:

1. Clean PostgreSQL migration, second upgrade, downgrade/upgrade on test DB.
2. Two-user/two-business tenant isolation test.
3. Duplicate batch leaves analytics totals unchanged.
4. `EXPLAIN (ANALYZE, BUFFERS)` for 90-day totals, pages, sources, actions, and paths.
5. Load profile completed without degrading the main LocalOS API.
6. Consent denied/allow/revoke checked in a real browser.
7. Rollback switches exercised without dropping data.

### Repeatable browser consent QA

The local fixture serves the real `frontend/public/tracker.js`, captures only its test batches in memory, and never connects to production:

```bash
tmux new -s webtrack-browser-qa
# From the local repository root:
python3 scripts/browser_qa_web_tracking.py --host 127.0.0.1 --port 8765
```

Open `http://127.0.0.1:8765/?utm_source=browser_qa` in a real browser and verify this sequence:

1. Initial `data-consent="denied"`: the page says anonymous IDs are absent and `GET /events` returns no batches.
2. Allow tracking: anonymous IDs are created and `session_start` plus `page_view` are captured.
3. Trigger the SPA button, focus the fixture input, and submit the prevented test form: `/services` is captured, but neither `private_query` nor `PRIVATE-INPUT-VALUE` appears in the captured JSON.
4. Revoke consent, trigger the post-revoke CTA, and wait longer than the five-second flush interval: the captured event count must remain unchanged.
5. The browser console must contain no tracker errors.

The fixture is a browser contract check, not an ingestion load test and not proof of a customer's cookie-banner implementation.

Rollout: one internal business for 3–5 days → 3–5 closed-pilot businesses → 10% → 25% → 50% → 100%, with at least 48–72 stable hours between percentage steps.

Run the bounded load profile only against an approved tracker because it creates analytics events:

```bash
python3 scripts/load_test_web_tracking.py \
  --target https://staging.example/api/tracking/events \
  --sites-file /approved/path/staging-trackers.txt \
  --requests 1000 --concurrency 100 --malformed-percent 3 --confirm-write
```

The sites file contains one `PUBLIC_TRACKER_ID=allowed.hostname` pair per line. Use 100 approved stage trackers for the full profile; `--tracker` plus `--hostname` remains available for a one-site smoke test. The report includes throughput and p50/p95/p99 latency.

The load gate is p95 within the configured budget, no network/5xx responses, healthy PostgreSQL connection usage, and no measurable degradation of the main LocalOS API. Final capacity must be measured on production-equivalent resources.
