# LocalOS: рабочий журнал и рекомендации допродаж

Статус: **beta, подготовка пилота**. Production-флаг в рамках этой доработки ещё не включён. Семидневный пилот и реальные устройства не проверены.

## Поведение

- `/dashboard/work-journal` и раздел «Рабочий журнал» Mini App используют общий Оператор. Telegram использует тот же обработчик. Голос в журнале отправляется сразу после распознавания; вопрос и пример не должны становиться фактом.
- Однозначное наблюдение сохраняется сразу; доступны исправление, отмена и история. Неоднозначный визит оставляет заметку без события визита и требует уточнения. Повтор запроса не создаёт вторую запись.
- `offered`, `declined`, `interested`, `performed` — операционные сведения сотрудников. Журнал не создаёт финансовые транзакции. Для финансов остаётся отдельное существующее подтверждение.
- Мастер определяется явной связью участника с мастером; видит собственные заметки и назначенные визиты. `manager` — администратор выбранного бизнеса/точки; `member` — сотрудник; `viewer` не получает право записи. Совпадение имени не выдаёт доступ.
- Владелец подтверждает запреты, приоритеты, формулировки, минимальное известное свободное время, привязки сотрудников и назначения визитов. Действие `work.policy.apply` исполняется через Action Orchestrator. Версия правил и отпечаток связок входят в подтверждение.
- Новый черновик связок не вытесняет подтверждённые рекомендации. Существующие редактирование/добавление связок в среднем чеке готовят подтверждение. История хранит предыдущие связки.
- Рекомендации содержат максимум три разрешённых дополнения. Неизвестные длительность/свободное время не считаются подтверждённой вместимостью расписания. Результаты предложений помечаются; правила из обратной связи автоматически не меняются.
- Временные правила интерпретируются по часовому поясу бизнеса из `business_finance_settings`; при отсутствии настройки требуется уточнение. Для визита учитывается его время.

## Хранение и API

Миграция `20260912_work_journal`, родитель `20260912_finance_daily`:
`business_work_journal`, `business_work_history`, `business_upsell_policies`, `business_master_bindings`; недостающий справочник `masters` и назначение `bookings.master_id`. События продолжают храниться в `averageticketevents` со ссылкой `journal_id`. Аудио не копируется в журнал.

API с проверкой пользователя и бизнеса:

| Метод | Адрес | Назначение |
|---|---|---|
| GET / POST | `/api/work-journal` | Поиск/дневной фильтр или создание наблюдения |
| PATCH | `/api/work-journal/<id>` | Исправление/отмена с `version`, `request_id` |
| GET | `/api/work-journal/<id>/history` | История доступной записи |
| POST | `/api/work-journal/recommendations` | Визит, день, следующий визит или группы услуг |
| POST | `/api/work-journal/policy/preview` | Подготовка изменения правил/связок/назначений |

Подтверждения: существующие `/api/operator/actions/<id>/confirm` и `/reject`. Чат остаётся `/api/operator/chat`; `input_context=work_journal` выбирает рабочий контекст, но не заменяет проверку прав. В API заметки `task_id` может ссылаться только на доступное задание `operator_async_jobs`.

## Выпуск

1. Проверить итоговые тесты и сохранённые свидетельства в `.agent/tasks/work-journal-20260912/`.
2. Создать **новую полную копию PostgreSQL**, проверить её читаемость. Старую копию предыдущего финансового выпуска не считать свежей.
3. Проверить текущую production-ревизию Alembic; доставить только относящиеся к выпуску backend-файлы и миграцию. Сохранить параллельные изменения других задач.
4. Применить Alembic из `/opt/seo-app`. Доставить изолированную frontend-сборку стандартным скриптом, не публикуя посторонние незакоммиченные изменения.
5. Добавить Riderra `edbd961a-273f-4f15-836e-33aacc0aa0e3` в `OPERATOR_WORK_JOURNAL_BUSINESS_IDS`. Параметр передаётся app, worker/operator-worker и telegram-bot. Изменение env требует пересоздания затронутых сервисов; полный rebuild не нужен.
6. Проверить Compose, свежие логи, localhost:8000, защищённые endpoints. Выполнить реальный STT → Оператор → журнал → TTS проход. Синтетические наблюдения нельзя выдавать за факты о Riderra.
7. На отдельном тестовом бизнесе проверить назначения двум мастерам, администратора, отказ и изменение владельцем. Отдельно — физические iOS/Android.
8. Семь дней наблюдать сохранения, уточнения, отмены, ошибки и подавленные дубли без текста сообщений. Расширение доступа — только после контрольного прохода и отсутствия нарушений прав/дублей/неподтверждённых изменений.

## Откат

Убрать пилотные ID из `OPERATOR_WORK_JOURNAL_BUSINESS_IDS`, пересоздать только затронутые сервисы. Журнал и история сохраняются. Когда применение подтверждённых правил отключено, рекомендации приостанавливаются с объяснением. Downgrade миграции намеренно не удаляет сведения.

## Открытые проверки выпуска

- Свежая резервная копия: пока не создана. На локальном диске около 0,3 ГБ; предыдущая полная копия около 1,6 ГБ. На сервере около 1,7 ГБ — недостаточный запас для безопасного нового полного backup и работы сервиса.
- Production-миграция и пилот: не выполнены.
- Реальные устройства, реальные сотрудники и семидневное использование: не выполнены; браузерная эмуляция их не заменяет.
- Непрерывное прослушивание, использование заметок для контента, клиентские отправки и банковские действия не входят в выпуск.
